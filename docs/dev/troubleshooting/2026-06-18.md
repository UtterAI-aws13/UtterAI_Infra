# Troubleshooting — 2026-06-18

NodePool taint isolation 적용, nvidia device plugin GPU pod Pending, Bedrock report pipeline 흐름 파악, cpu-worker Karpenter eviction 리스크 대응 기록.

## 1. cpu-worker / batch-worker NodePool taint isolation 적용

### 배경

기존 cpu-worker / batch-worker NodePool에 taint가 없어 다른 워크로드가 동일 노드에 스케줄될 수 있었다. NodePool에 전용 taint를 추가하고 대상 Deployment에 toleration을 추가해 격리를 완성했다.

### 변경 내용

**`k8s/platform/karpenter/base/nodepools.yaml`**

cpu-worker, batch-worker NodePool 양쪽에 taint 추가:

```yaml
taints:
  - key: dedicated
    value: worker
    effect: NoSchedule
```

**`k8s/apps/ai-worker/base/cpu-worker-deployment.yaml`**  
**`k8s/apps/ai-worker/base/batch-worker-deployment.yaml`**

```yaml
tolerations:
  - key: dedicated
    operator: Equal
    value: worker
    effect: NoSchedule
```

### 결과

- cpu-worker, batch-worker 전용 노드에만 해당 Pod가 스케줄됨
- 두 NodePool이 같은 `dedicated=worker:NoSchedule` taint를 공유하므로, cpu-worker 전용 노드에 batch-worker Pod도 착지할 수 있음 (nodeSelector로 workload 레이블 기준 분리 유지)

## 2. nvidia device plugin DaemonSet — GPU pod Pending (`Insufficient nvidia.com/gpu`)

### 증상

GPU NodePool 노드가 프로비저닝됐음에도 ml-gpu-worker Pod가 `Pending` 상태 지속.

```
Events:
  Warning  FailedScheduling  Insufficient nvidia.com/gpu
```

### 원인

GPU NodePool은 두 개의 taint를 갖는다:

```yaml
taints:
  - key: dedicated
    value: ai-gpu
    effect: NoSchedule
  - key: nvidia.com/gpu
    value: "true"
    effect: NoSchedule
```

nvidia device plugin DaemonSet에는 `dedicated=ai-gpu:NoSchedule` toleration만 있고 `nvidia.com/gpu:NoSchedule` toleration이 없어서, DaemonSet Pod가 GPU 노드에 스케줄되지 못했다.

DaemonSet이 GPU 노드에 뜨지 않으면 GPU 리소스가 kubelet에 등록되지 않아, ml-gpu-worker Pod가 `nvidia.com/gpu: 1` 리소스를 요청해도 클러스터 어디서도 충족되지 않는다.

### 해결

`terraform/modules/eks-addons/main.tf` nvidia device plugin Helm values에 toleration 추가:

```hcl
tolerations = [
  {
    key      = "dedicated"
    operator = "Equal"
    value    = "ai-gpu"
    effect   = "NoSchedule"
  },
  {
    key      = "nvidia.com/gpu"
    operator = "Exists"
    effect   = "NoSchedule"
  }
]
```

`nvidia.com/gpu` taint의 value는 노드마다 다를 수 있어 `operator: Exists`로 처리.

```bash
cd terraform/environments/dev/04-addons
terraform apply
```

### 결과

nvidia device plugin DaemonSet이 GPU 노드에 정상 스케줄되어 `nvidia.com/gpu` 리소스가 등록되고, ml-gpu-worker Pod가 Running 상태로 전환됨.

### 핵심 교훈

GPU 노드에 여러 taint가 있는 경우, 해당 노드에 반드시 떠야 하는 DaemonSet(nvidia device plugin, node-exporter 등)에 **모든 taint에 대한 toleration**이 있어야 한다. 하나라도 빠지면 DaemonSet이 스케줄되지 않아 GPU 리소스가 미등록 상태가 된다.

## 4. cpu-worker Pod 재시작처럼 보이는 현상 — 실제 노드 이동

### 증상

cpu-worker Pod가 내려갔다가 새로 올라오는 현상. 9분대 Running인 Pod 1개만 존재.

### 원인

Karpenter `consolidationPolicy: WhenEmptyOrUnderutilized`에 의해 저부하 노드가 통합될 때 Pod가 SIGTERM을 받고 다른 노드로 재스케줄되는 것. Pod 재시작(restartCount 증가)이 아니라 **노드 이동**이다.

- KEDA `minReplicaCount: 1`이 설정되어 있어 Pod 수는 0으로 내려가지 않음
- `terminationGracePeriodSeconds: 60`이 적용되어 graceful shutdown 시간 보장
- SQS 메시지의 `VisibilityTimeout`(preprocess: 300s, report: 600s) 내에 재처리가 시작되므로 메시지 유실 없음

### 결론

정상 동작. cpu-worker는 SQS 기반 idempotent 처리 구조이므로 노드 이동 시 메시지가 visibility timeout 후 다시 보이고 재처리된다.

## 5. Bedrock report pipeline 흐름 파악 및 누락 구현 발견

```

  → SQS audio-preprocess-queue 발행
  → cpu-worker: _run_preprocess_loop 수신, STT 전처리
  → SQS gpu-inference-queue 발행
  → ml-gpu-worker: asyncio.run(_run())  ← GPU 추론
  → (누락) BE handle_internal_callback() HTTP POST 호출 필요
  → SQS report-analysis-queue 발행  ← BE.finalize()에서 별도 발행
  → cpu-worker: _run_report_loop 수신, Bedrock 호출

```

### 누락 발견

`UtterAI_AI/app/workers/ml_gpu_worker.py`에서 GPU 추론 완료 후 BE `handle_internal_callback()`을 호출하는 코드가 없음.

```python
asyncio.run(_run())
# ← 이 위치에 BE POST /api/v1/internal/analysis-results/callback 호출 필요
sqs.delete_message(...)
```

BE측 엔드포인트(`POST /api/v1/internal/analysis-results/callback`)와 `TranscriptService.handle_internal_callback()`은 이미 구현되어 있음.

### 관련 파일

| 레포 | 파일 | 역할 |
|------|------|------|
| AI | `app/workers/cpu_worker.py` | preprocess + report 두 루프 실행 |
| AI | `app/workers/ml_gpu_worker.py` | GPU 추론, BE 콜백 누락 |
| AI | `app/pipelines/bedrock_client.py` | `invoke_claude()` via bedrock-runtime |

| BE | `app/api/v1/api.py` | `/internal/analysis-results` 라우터 마운트 |

### 액션 아이템

**AI 팀**: `ml_gpu_worker.py`의 `asyncio.run(_run())` 완료 직후 BE `handle_internal_callback()` HTTP POST 호출 추가 필요.

## 6. cpu-worker consolidateAfter 30s → 5m (Karpenter eviction 리스크 대응)

### 문제

cpu-worker는 Bedrock API(`bedrock-runtime invoke_model`)를 호출하는 `_run_report_loop`를 실행한다.

Bedrock 호출 중에는 CPU 사용률이 낮아 Karpenter가 노드를 "저활용(Underutilized)" 판정한다. 기존 `consolidateAfter: 30s` 설정에서는:

1. Karpenter가 30초 후 consolidation 결정
2. Pod에 SIGTERM 발송
3. `terminationGracePeriodSeconds: 60` 내 작업 미완료 시 SIGKILL
4. SQS 메시지가 `VisibilityTimeout=600s` 동안 in-flight 상태로 묶임
5. 600초 후 재처리 — 사용자 입장에서 10분 지연

Bedrock 응답 자체는 실측 8.5s 내외로 빠르나, I/O 대기 중 CPU가 낮아 eviction 트리거 조건을 충족한다.

### 해결

`k8s/platform/karpenter/base/nodepools.yaml` cpu-worker NodePool:

```yaml
disruption:
  consolidationPolicy: WhenEmptyOrUnderutilized
  consolidateAfter: 5m  # 30s → 5m
```

5분이면 Bedrock 호출 완료 및 후속 처리를 충분히 수용한다.

### 왜 consolidateAfter가 중요한가

| 설정 | 의미 |
|------|------|
| `consolidationPolicy: WhenEmpty` | 노드에 Pod가 하나도 없을 때만 통합 |
| `consolidationPolicy: WhenEmptyOrUnderutilized` | 저활용 노드도 통합 대상 |
| `consolidateAfter` | 통합 조건이 충족된 후 **실제 eviction 전 대기 시간** |

`consolidateAfter: 30s`는 Bedrock처럼 I/O 바운드 작업(CPU 낮지만 응답 대기 중)에서 조기 eviction 리스크가 있다.

### 참고: terminationGracePeriodSeconds와의 관계

`consolidateAfter`는 eviction 결정까지의 대기, `terminationGracePeriodSeconds`는 SIGTERM 이후 SIGKILL까지의 유예 시간이다. 두 값이 독립적으로 작동하므로 `consolidateAfter`를 늘리는 것이 핵심 해결책이다.

현재 `terminationGracePeriodSeconds: 60`은 Bedrock 응답(실측 8.5s)에는 충분하나, 실제 작업 패턴에 따라 향후 조정이 필요할 수 있다.

## 7. ml-gpu-worker 콜드 스타트 + SQS Visibility Timeout — 음성 분석 10분 지연 현상

### 증상

음성 파일을 업로드하고 분석을 요청했을 때 약 10분 동안 아무 응답이 없다가, 10분이 지난 후 재시도하면 즉시 처리되는 현상.

---

### 파이프라인 흐름

```
음성 업로드 (BE)
  │
  ▼
audio-preprocess-queue  (visibility_timeout=300s)
  │  cpu-worker 수신 → STT 전처리 (빠름, 수십 초)
  ▼
gpu-inference-queue     (visibility_timeout=600s)  ← 문제 구간
  │  ml-gpu-worker 수신 → GPU 추론 (Whisper 등)
  ▼
report-analysis-queue   (visibility_timeout=900s)
  │  cpu-worker 수신 → Bedrock 호출 → 분석 완료
```

---

### SQS 핵심 개념: Visibility Timeout / NotVisible

#### Visibility Timeout이란

SQS는 메시지를 worker가 받아가면 **즉시 삭제하지 않고**, 설정된 시간 동안 다른 consumer에게 보이지 않게 숨긴다.  
이 숨김 상태가 끝날 때까지 worker가 `DeleteMessage`를 호출하지 않으면 메시지는 다시 큐에 노출(visible)된다.

```
t=0s    메시지 도착 → worker가 ReceiveMessage
        └─ 즉시 삭제 X
        └─ visibility_timeout 동안 다른 worker에게 안 보임 (NotVisible)

t=600s  DeleteMessage 없이 timeout 만료
        └─ 메시지 다시 visible
        └─ receiveCount += 1
        └─ receiveCount >= maxReceiveCount 이면 DLQ로 이동
```

**왜 이렇게 설계됐나?**  
worker가 처리 도중 crash되면 메시지를 복구할 수 있도록 하기 위함이다. worker는 처리가 완전히 끝난 뒤에만 `DeleteMessage`를 호출한다.

#### `get-queue-attributes` 응답의 각 카운터

| 필드 | 의미 |
|------|------|
| `ApproximateNumberOfMessages` | 큐에서 꺼내갈 수 있는 메시지 수 (아무도 받지 않은 상태) |
| `ApproximateNumberOfMessagesNotVisible` | worker가 ReceiveMessage했지만 아직 DeleteMessage를 보내지 않은 메시지 수. 현재 처리 중이거나 timeout 임박 상태 |
| `ApproximateNumberOfMessagesDelayed` | DelaySeconds 설정으로 아직 큐에 나타나지 않은 메시지 수 |

**NotVisible이 0이 아닌 경우 두 가지 해석:**

| 상태 | 의미 |
|------|------|
| worker가 정상 처리 중 | 곧 DeleteMessage 호출 예정. 정상 |
| worker가 timeout 내 처리 못 함 | visibility 만료 후 메시지 다시 visible로 전환 → 재처리 또는 DLQ 이동 |

---

### 실측 AWS 큐 상태 (2026-06-18 조회)

```
gpu-inference-queue:
  ApproximateNumberOfMessages           : 0
  ApproximateNumberOfMessagesNotVisible : 1   ← 처리 중인 메시지 존재
  VisibilityTimeout                     : 600
  maxReceiveCount (DLQ redrive)         : 2

audio-preprocess-queue:
  ApproximateNumberOfMessages           : 0
  ApproximateNumberOfMessagesNotVisible : 0
  VisibilityTimeout                     : 300
  maxReceiveCount (DLQ redrive)         : 3

gpu-inference-dlq:
  ApproximateNumberOfMessages           : 0   ← 현재는 DLQ 도달 없음
```

조회 시점에 `gpu-inference-queue`에 처리 중인 메시지 1개 확인됨.  
DLQ에는 메시지가 없으나, 콜드 스타트 타이밍에 따라 간헐적으로 DLQ에 쌓일 수 있는 구조다.

---

### 근본 원인

#### 원인 1 (핵심): GPU 콜드 스타트 시간 ≈ visibility_timeout (600s)

ml-gpu-worker의 KEDA ScaledObject `minReplicaCount: 0` 설정으로 평소에 pod가 0개다.  
첫 분석 요청이 들어오면 다음 순서로 콜드 스타트가 발생한다:

```
t=0s    메시지 → gpu-inference-queue 도착
        KEDA 감지 → ml-gpu-worker 0 → 1 스케일업

t=0~?   Karpenter GPU 노드 프로비저닝
          EC2 GPU 인스턴스 부팅
          GPU 드라이버 초기화
          nvidia device plugin 준비
          대용량 ML 컨테이너 이미지 pull (Whisper 등)
          ML 모델 GPU 메모리 로딩

        ← 이 전체 시간이 600초에 근접하거나 초과

t=600s  visibility_timeout 만료
        메시지 다시 visible → receiveCount = 2
        (이 시점에 worker가 막 뜨고 있거나 아직 준비 안 됨)

        maxReceiveCount = 2 이므로 다음 수신 실패 시 DLQ 이동
```

**10분 후 재시도하면 바로 되는 이유:**  
GPU 노드, worker pod, ML 모델이 이미 메모리에 올라와 있는 warm 상태이기 때문에  
메시지를 받자마자 수초 내 처리하고 `DeleteMessage` 호출까지 완료된다.

#### KEDA / Karpenter의 역할과 한계

KEDA와 Karpenter는 스케일링 결정과 노드 프로비저닝 속도를 개선하지만, 콜드 스타트 자체를 없애지는 않는다.

- **KEDA**: SQS 메시지 수 기반으로 HPA보다 빠르게 스케일업을 결정
- **Karpenter**: Cluster Autoscaler보다 빠르게 GPU 노드를 프로비저닝

그 이후의 EC2 부팅 / GPU 드라이버 초기화 / 이미지 pull / 모델 로딩(합계 5~10분)은 두 컴포넌트 모두 제어할 수 없다. `minReplicaCount: 0`인 한 첫 요청 콜드 스타트는 피할 수 없는 구조적 한계다.

#### 원인 2: 처리 중 Visibility Timeout 연장 미구현

GPU 추론 작업이 길어질 경우 worker가 SQS `ChangeMessageVisibility` API를 주기적으로 호출해서 timeout을 연장해야 한다.  
현재 `ml_gpu_worker.py`에 이 heartbeat 로직이 없으면, 실제 GPU 추론 시간이 600s를 넘는 긴 음성 파일에서도 동일한 증상이 발생한다.

#### 원인 3: maxReceiveCount = 2 가 너무 낮음

콜드 스타트로 1번 실패하면 남은 기회가 1번뿐이다.  
2번째 시도도 타이밍 문제로 실패하면 DLQ로 직행한다.

---

### Visibility Timeout 적용 우선순위

`receive_message` 호출의 `VisibilityTimeout` 파라미터가 큐 기본값보다 우선 적용된다.

```python
# ml_gpu_worker.py — 현재 문제
sqs.receive_message(
    VisibilityTimeout=600,  # 큐 기본값을 덮어씀
)
```

Terraform에서 큐를 1800으로 변경해도, worker 코드에서 600을 명시하면 실제 타임아웃은 600이다. **두 곳을 함께 수정해야 효과가 있다.**

### On-Demand G/VT 인스턴스 Quota 4 → 32 vCPU 변경

이 변경은 **동시에 실행 가능한 GPU 인스턴스 vCPU 총합 상한**을 늘린 것이다.

```
4 vCPU  → g4dn.xlarge 1대만 동시 실행 가능
32 vCPU → g4dn.xlarge 최대 8대 동시 실행 가능
```

- **이점**: 복수의 동시 분석 요청을 병렬 처리 가능. 이전엔 2번째 GPU 노드 프로비저닝 시 quota 초과로 실패했음.
- **콜드 스타트 해결 여부**: 해결 안 됨. Quota는 "몇 대까지"의 상한이며, "얼마나 빨리" 뜨는지와 무관하다.

### 권장 수정 사항

#### 인프라 레벨 (즉각 조치 가능)

**`terraform/modules/sqs/main.tf`**

```hcl
# gpu_inference 큐
visibility_timeout_seconds = 1800  # 600 → 1800 (30분)

redrive_policy = jsonencode({
  deadLetterTargetArn = aws_sqs_queue.gpu_inference_dlq.arn
  maxReceiveCount     = 3           # 2 → 3
})
```

visibility_timeout을 1800s(30분)으로 늘리면 콜드 스타트 이후 충분한 처리 시간을 확보한다.  
`maxReceiveCount`를 3으로 늘리면 콜드 스타트 1회 실패 후에도 2번의 재시도 기회가 남는다.

#### 앱 레벨 (근본 해결)

**`UtterAI_AI/app/workers/ml_gpu_worker.py`** — ChangeMessageVisibility heartbeat 추가

```python
import threading

def _extend_visibility(sqs_client, queue_url, receipt_handle, stop_event, interval=300):
    """처리 중 주기적으로 visibility timeout 연장."""
    while not stop_event.wait(interval):
        try:
            sqs_client.change_message_visibility(
                QueueUrl=queue_url,
                ReceiptHandle=receipt_handle,
                VisibilityTimeout=1800
            )
        except Exception:
            break

stop_event = threading.Event()
heartbeat = threading.Thread(
    target=_extend_visibility,
    args=(sqs_client, queue_url, receipt_handle, stop_event),
    daemon=True,
)
heartbeat.start()

try:
    asyncio.run(_run())  # GPU 추론
    sqs_client.delete_message(QueueUrl=queue_url, ReceiptHandle=receipt_handle)
finally:
    stop_event.set()
```

이 패턴으로 GPU 추론 시간이 얼마나 걸리든 관계없이 메시지가 만료되지 않는다.

---

### 현재 상태 및 액션 아이템

| 항목 | 상태 |
|------|------|
| Terraform gpu_inference visibility_timeout 600 → 1800 | ✅ 완료 |
| Terraform gpu_inference maxReceiveCount 2 → 3 | ✅ 완료 |
| SQS 변수 하드코딩 → 변수 분리 리팩토링 | ✅ 완료 |
| AI 팀: `receive_message` VisibilityTimeout=600 제거 | ⬜ AI 팀 요청 필요 |
| AI 팀: heartbeat (ChangeMessageVisibility) 패턴 추가 | ⬜ AI 팀 요청 필요 |
| 콜드 스타트 근본 해결 방안 결정 (스케줄/EFS/조합) | ⬜ 팀 결정 필요 (docs/shared/gpu-cold-start-strategy.md 참고) |

### 핵심 교훈

1. **SQS visibility_timeout은 "처리 완료까지의 최대 허용 시간"이다.** 콜드 스타트 시간을 포함한 end-to-end 처리 시간보다 반드시 길어야 한다.
2. **scale-to-zero(minReplicaCount: 0) 환경에서는 콜드 스타트가 SQS timeout 설계에 반드시 반영되어야 한다.** GPU 노드는 특히 프로비저닝 + 모델 로딩 시간이 길다.
3. **장시간 처리 작업에는 ChangeMessageVisibility heartbeat가 필수다.** visibility_timeout을 늘리는 것만으로는 실제 추론 시간이 가변적인 케이스를 커버할 수 없다.
4. **NotVisible 카운터가 0이 아니면 현재 처리 중인 메시지가 있다는 의미다.** 이 상태에서 timeout이 만료되면 재처리 또는 DLQ 이동이 발생한다.
