# Troubleshooting — 2026-06-24

readOnlyRootFilesystem 적용 후 HuggingFace cache 크래시, GPU worker IRSA reports 버킷 PutObject 누락, prod ConfigMap S3 env var 이름 불일치(BE main vs dev), Kubecost cluster_id 누락, CloudFront WAF 추가 기록.

---

## 1. GPU Worker 크래시 — readOnlyRootFilesystem으로 HuggingFace cache 경로 차단

### 1-1. 발견된 상태

prod 분석 작업이 실행되지 않음. GPU worker pod가 모델 로딩 단계에서 크래시:

```
PermissionError: [Errno 13] Permission denied: '/home/appuser/.cache/huggingface/...'
```

HF_HOME이 `/tmp/huggingface`로 설정되어 있었음에도 pyannote 라이브러리가 `/home/appuser/.cache`에 직접 쓰려다 실패.

### 1-2. 원인 분석

전날(2026-06-23) `readOnlyRootFilesystem: true`를 전체 워크로드에 적용하면서 `/tmp`에 emptyDir을 마운트하고 `HF_HOME=/tmp/huggingface`를 설정했다.

그러나 `pyannote.audio`의 `Pipeline.from_pretrained()`는 `HF_HOME`과 별도로 `~/.cache`(`/home/appuser/.cache`)에 캐시 디렉터리를 만들려는 코드 경로가 존재한다. 컨테이너 이미지의 `/home/appuser/.cache`는 read-only root filesystem에 속해 쓰기 불가.

```
readOnlyRootFilesystem: true
→ /home/appuser/.cache: 읽기 전용
→ pyannote Pipeline.from_pretrained() 크래시
```

### 1-3. 해결

`k8s/apps/ai-worker/overlays/prod/patch-deployment.yaml`에 `/home/appuser/.cache`용 emptyDir 추가 (PR #299):

```yaml
volumes:
  - name: tmp
    emptyDir: {}
  - name: hf-cache
    emptyDir: {}

volumeMounts:
  - name: tmp
    mountPath: /tmp
  - name: hf-cache
    mountPath: /home/appuser/.cache
```

### 1-4. 핵심 교훈

`readOnlyRootFilesystem: true`를 적용할 때 라이브러리가 홈 디렉터리 하위에 캐시를 쓰는 경우를 별도로 검증해야 한다. `HF_HOME` 설정만으로는 pyannote처럼 내부적으로 `~/.cache`를 직접 참조하는 라이브러리를 막을 수 없다. 워크로드별로 `/home/<user>/.cache` 쓰기 여부를 미리 확인하고 emptyDir을 추가해야 한다.

## 2. GPU Worker IRSA — reports 버킷 PutObject 권한 누락

### 2-1. 발견된 상태

GPU worker가 분석 완료 후 `transcript_draft.json`을 S3에 업로드하는 단계에서 AccessDenied:

```
An error occurred (AccessDenied) when calling the PutObject operation:
User: arn:aws:sts::032886669461:assumed-role/utterai-prod-ai-ml-gpu-irsa-role/...
is not authorized to perform: s3:PutObject on resource: utterai-prod-reports/...
```

transcripts 버킷에는 정상 업로드됨.

### 2-2. 원인 분석

`terraform/modules/irsa/main.tf`의 `ai_ml_gpu` 정책:

```hcl
# 수정 전
{
  Effect   = "Allow"
  Action   = ["s3:PutObject"]
  Resource = ["${var.transcripts_bucket_arn}/*"]
}
# reports_bucket_arn 변수는 선언되어 있었으나 정책 statement에 포함되지 않음
```

`reports_bucket_arn` 변수가 모듈에 이미 정의되어 있었지만, `ai_ml_gpu` 정책 statement에 실제로 추가되지 않은 채 방치됨.

### 2-3. 해결

`terraform/modules/irsa/main.tf`에 reports 버킷 PutObject statement 추가 (PR #300):

```hcl
{
  Effect   = "Allow"
  Action   = ["s3:PutObject"]
  Resource = ["${var.transcripts_bucket_arn}/*"]
},
{
  Effect   = "Allow"
  Action   = ["s3:PutObject"]
  Resource = ["${var.reports_bucket_arn}/*"]
},
```

```bash
cd terraform/environments/prod/03-services && terraform apply
# IAM 정책 즉시 반영
```

### 2-4. 핵심 교훈

새 S3 버킷을 IRSA 모듈에 변수로 추가할 때 정책 statement에도 반드시 함께 추가해야 한다. 변수 선언과 정책 statement는 별개라 한쪽만 추가해도 오류가 발생하지 않아 실제 사용 시점까지 누락을 발견하기 어렵다. IRSA 모듈 수정 PR은 변수 추가 + 정책 statement 추가를 하나의 단위로 묶어 리뷰해야 한다.

## 3. prod API ConfigMap S3 env var 불일치 — BE main vs dev 브랜치 차이

### 3-1. 발견된 상태

prod API에서 S3 presigned URL 생성 실패. 업로드 시도 시 에러 반환. dev 환경은 정상.

```
# prod API 로그
KeyError: 'S3_BUCKET_AUDIO'
```

### 3-2. 원인 분석

2단계에 걸친 불일치가 동시에 발생:

**1단계**: 전날(2026-06-23) k8s-legacy에서 dev S3 env var를 BE PR #74 기준으로 `RAW_AUDIO_BUCKET → S3_BUCKET_AUDIO`로 변경했다 (PR #290).

**2단계**: 같은 PR #290의 맥락에서 `k8s/apps/backend/overlays/prod/patch-configmap.yaml`도 동일하게 `S3_BUCKET_AUDIO` 등으로 업데이트됐다 (PR #295 첫 버전).

그러나 prod는 현재 BE main 브랜치(`debf7b8`)를 실행 중이고, BE main은 아직 PR #74가 머지되지 않아 여전히 `RAW_AUDIO_BUCKET`, `TEMPLATE_BUCKET` 변수명을 읽는다. prod ConfigMap이 dev 브랜치 기준 이름으로 잘못 업데이트되어 BE main이 해당 변수를 찾지 못함.

```
dev 브랜치 (PR #74 머지됨):     S3_BUCKET_AUDIO / S3_BUCKET_TEMPLATE
prod BE main (PR #74 미머지): RAW_AUDIO_BUCKET / TEMPLATE_BUCKET
prod ConfigMap (잘못된 상태): S3_BUCKET_AUDIO / S3_BUCKET_TEMPLATE
                                                ↑ 불일치 → KeyError
```

### 3-3. 해결

`k8s/apps/backend/overlays/prod/patch-configmap.yaml`을 prod BE main 기준으로 롤백 (PR #295):

```yaml
# 수정 후 — prod BE main(debf7b8) 기준
RAW_AUDIO_BUCKET: "utterai-prod-raw-audio"
TEMPLATE_BUCKET: "utterai-prod-template"
# S3_BUCKET_TRANSCRIPT 제거 (BE main에 없는 변수)
```

BE main에 PR #74가 머지될 때 prod ConfigMap도 함께 업데이트 예정.

### 3-4. 핵심 교훈

infra ConfigMap의 env var 이름은 **현재 prod에 배포된 BE 브랜치**를 기준으로 관리해야 한다. dev ConfigMap과 prod ConfigMap은 BE 브랜치가 다를 때 각자 독립적으로 유지해야 한다. BE PR이 prod에 배포되기 전에 infra ConfigMap을 미리 바꾸면 배포 즉시 장애가 발생한다.

## 4. Kubecost Federated Storage — cluster_id 외부 레이블 누락

### 4-1. 발견된 상태

Kubecost federated cost 뷰에서 클러스터별 비용 분류가 되지 않고 모든 데이터가 unnamed cluster로 집계됨.

### 4-2. 원인 분석

Kubecost federated storage는 Prometheus의 `external_labels`에서 `cluster_id`를 읽어 클러스터별로 비용 데이터를 구분한다. Helm values에서 내장 Prometheus를 비활성화(`enabled: false`)할 때 `global.external_labels` 설정도 함께 제거됐다.

```hcl
# 수정 전
prometheus = {
  server = {
    enabled = false
    # external_labels 없음
  }
}
```

### 4-3. 해결

`terraform/modules/eks-addons/main.tf` Kubecost Helm values 수정 (PR #294):

```hcl
prometheus = {
  server = {
    enabled = false
    global = {
      external_labels = {
        cluster_id = var.cluster_name
      }
    }
  }
}
```

### 4-4. 핵심 교훈

Kubecost federated storage에서 `prometheus.server.enabled = false`로 내장 Prometheus를 끌 때도 `global.external_labels.cluster_id`는 반드시 설정해야 한다. 없으면 멀티클러스터 환경에서 비용 데이터 귀속이 불가능하다.

## 5. CloudFront WAF — Frontend Edge 보호 추가

### 5-1. 배경

prod frontend CloudFront 배포에 WAF(Web Application Firewall)가 없어 기본적인 웹 공격 필터링이 미적용 상태.

### 5-2. 구성 내용 (PR #293)

`terraform/environments/prod/04-addons/main.tf`에 CloudFront WAF 추가:

```hcl
resource "aws_wafv2_web_acl" "frontend_edge" {
  count    = var.cloudfront_waf_enabled ? 1 : 0
  provider = aws.us_east_1   # CloudFront WAF는 반드시 us-east-1
  name     = "${var.project_name}-${var.environment}-frontend-edge-waf"
  scope    = "CLOUDFRONT"
  ...
}
```

`scope = "CLOUDFRONT"`인 WAF는 **반드시 `us-east-1` 리전에 생성**해야 한다. ap-northeast-2 provider로 생성하면 에러.

### 5-3. 핵심 교훈

CloudFront WAF(`scope = "CLOUDFRONT"`)는 us-east-1 리전 리소스다. Terraform에서 별도의 `aws.us_east_1` provider alias를 설정해야 한다. 리전 실수 시 에러 메시지가 불명확하므로 WAF scope와 리전 매핑을 코드 주석으로 명시해두는 것이 좋다.

---

## 6. 핵심 교훈 종합

1. **`readOnlyRootFilesystem: true` 적용 시 라이브러리가 `~/.cache`에 직접 쓰는 경우를 검증해야 한다.** `HF_HOME` 환경변수 설정만으로는 pyannote 등 일부 라이브러리의 내부 캐시 경로를 제어할 수 없다.

2. **IRSA 모듈에 새 S3 버킷 변수를 추가할 때는 정책 statement도 반드시 함께 추가한다.** 변수 선언과 정책 적용은 별개 작업이다.

3. **prod ConfigMap의 env var 이름은 현재 prod에 실행 중인 BE 커밋 기준으로 유지한다.** dev 브랜치 변경을 prod에 미리 반영하면 즉시 장애가 발생한다.

4. **Kubecost federated storage는 내장 Prometheus를 끄더라도 `global.external_labels.cluster_id`를 설정해야 클러스터별 비용 분류가 가능하다.**

5. **CloudFront WAF는 `aws.us_east_1` provider alias가 필요하다.** scope = CLOUDFRONT 리소스는 us-east-1만 지원한다.
