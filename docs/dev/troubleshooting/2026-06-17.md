# Troubleshooting — 2026-06-17

KEDA + Karpenter Phase 2 전환(PR #180) 직후 클러스터에서 발생한 문제 4건 기록.

---

## 1. EC2NodeClass READY=False — "Failed to detect the cluster CIDR"

### 증상

```bash
$ kubectl get ec2nodeclass default
NAME      READY   AGE
default   False   ...

$ kubectl get ec2nodeclass default -o jsonpath='{.status.conditions[?(@.type=="Ready")]}'
{"message":"Failed to detect the cluster CIDR","reason":"NodeClassNotReady","status":"False","type":"Ready"}
```

모든 서브 컨디션(AMIsReady, SubnetsReady, SecurityGroupsReady, InstanceProfileReady, ValidationSucceeded)은 True인데 최종 Ready만 False.

### 원인

Karpenter v1.x는 EC2NodeClass reconcile 시 `eks:DescribeCluster`를 호출해 클러스터 Service CIDR을 가져온다.
PR #180에서 생성한 Karpenter IRSA 정책(`utterai-dev-karpenter-policy`)에 이 권한이 누락되어 있었다.

Karpenter Pod 로그에 AccessDeniedException이 찍히지만, Ready 컨디션 메시지는 일반적인 "Failed to detect the cluster CIDR"로만 노출되어 원인 파악이 늦었다.

### 해결

1. `terraform/modules/irsa/main.tf` Karpenter 정책에 권한 추가

```hcl
{
  Effect   = "Allow"
  Action   = ["eks:DescribeCluster"]
  Resource = ["arn:aws:eks:${var.aws_region}:${var.aws_account_id}:cluster/*"]
}
```

2. 즉시 반영을 위해 targeted apply

```bash
terraform apply -target=module.irsa.aws_iam_role_policy.karpenter
```

3. Pod 재시작으로 새 IRSA 토큰 수령 (토큰은 Pod 기동 시 발급, 런타임 중 자동 갱신 안 됨)

## 2. Karpenter Pod 재시작 차단 — topology spread constraints

### 증상

`kubectl rollout restart deployment/karpenter -n karpenter` 실행 후 새 Pod가 Pending 상태로 멈춤.

```
Events:
  Warning  FailedScheduling  1 Insufficient cpu, topology spread constraints
```

기존 Pod(175m+ 실행 중)가 여전히 active reconciler로 동작해 새 IRSA 토큰을 받지 못함.

### 원인

Karpenter Helm 기본값은 `replicas=2`, `topologySpreadConstraints` 설정이 있어 두 Pod가 다른 노드에 스케줄돼야 한다.
dev 클러스터의 가용 노드가 부족해 두 번째 Pod를 띄울 수 없는 상황이었다.

### 해결

```bash
# 단일 레플리카로 축소 후 기존 Pod 강제 삭제
kubectl scale deployment/karpenter -n karpenter --replicas=1
kubectl delete pod -n karpenter -l app.kubernetes.io/name=karpenter --force
```

새 Pod가 단일 노드에 기동되어 fresh IRSA 토큰 수령 완료.

> **참고**: 정상 운영 중에는 `kubectl rollout restart`로 rolling update 가능 (노드 여유가 있을 때).
> HA가 필요 없는 dev 환경에서는 `replicas=1`을 유지해도 무방.

## 3. EC2NodeClass 상태가 IAM 수정 후에도 갱신되지 않음

### 증상

IAM 정책 반영 및 Pod 재시작 완료 후에도 `kubectl get ec2nodeclass default`가 여전히 `READY=False` 표시.
`lastTransitionTime`이 수 시간 전 그대로.

### 원인

Karpenter의 nodeclass 컨트롤러는 EC2NodeClass 리소스의 `generation`이 변경될 때 재reconcile 한다.
annotation 패치는 `generation`을 올리지 않으므로 재조정이 트리거되지 않았다.

### 해결

`spec` 필드를 변경해 `generation`을 bump하면 컨트롤러가 즉시 재reconcile한다.

```bash
# 무해한 태그 하나 추가 → generation 증가 → 재reconcile 트리거
kubectl patch ec2nodeclass default --type=json \
  -p '[{"op":"add","path":"/spec/tags/reconcile","value":"trigger"}]'
```

약 10-20초 후 `READY=True` 로 전환됨.

> **주의**: kustomize apply 이후에는 해당 임시 태그가 제거된다. 운영 환경에서는 kustomize 적용으로 reconcile을 트리거하는 것이 더 깔끔하다.

## 4. kubectl apply -k 실패 — amiSelectorTerms: Required value

### 증상

```bash
$ kubectl apply -k k8s/platform/dev

Error from server (Invalid): EC2NodeClass.karpenter.k8s.aws "default" is invalid:
  spec.amiSelectorTerms: Required value
```

패치가 `{"spec":{"amiSelectorTerms":null}}`을 생성해 검증에 실패.

### 원인

팀원이 클러스터에 직접 `amiSelectorTerms: [{alias: al2023@latest}]`를 적용했지만, 코드의 base manifest(`k8s/platform/karpenter/base/ec2nodeclass.yaml`)는 deprecated `amiFamily: AL2023`만 사용하고 있었다.

Karpenter v1.x에서 `amiFamily`는 여전히 유효하지만, 클러스터 오브젝트에 `amiSelectorTerms`가 이미 존재하는 상태에서 kustomize가 이를 포함하지 않은 manifest를 apply하면, 서버사이드 패치가 `amiSelectorTerms: null`로 덮어쓰려 시도해 필수 필드 검증 오류가 발생한다.

### 해결

base manifest를 `amiSelectorTerms` 방식으로 교체.

```yaml
# k8s/platform/karpenter/base/ec2nodeclass.yaml (변경 전)
spec:
  amiFamily: AL2023

# 변경 후
spec:
  amiSelectorTerms:
    - alias: al2023@latest
```

> **교훈**: 클러스터에 직접 적용한 변경사항은 반드시 동일 세션에서 코드에도 반영해야 한다. 다음 kustomize apply 시 drift가 발생해 예상치 못한 오류가 생길 수 있다.

## 5. VPC CNI v1.18.1 스키마 변경 — ENABLE_NETWORK_POLICY

> 팀원이 직접 클러스터에서 해결한 이슈. 코드 반영만 진행.

### 증상

VPC CNI addon upgrade 후 Terraform apply 시 addon 검증 오류.

### 원인

VPC CNI v1.18.1에서 network policy 설정 키가 이동됨.

| 위치 | 이전 (≤v1.17.x) | 이후 (v1.18.1+) |
|------|----------------|----------------|
| 키 경로 | `env.ENABLE_NETWORK_POLICY` | 루트 `enableNetworkPolicy` |

### 해결

```hcl
# terraform/modules/eks/main.tf (변경 전)
configuration_values = jsonencode({
  env = {
    ENABLE_PREFIX_DELEGATION = "true"
    WARM_PREFIX_TARGET       = "1"
    ENABLE_NETWORK_POLICY    = "true"   # ← 잘못된 위치
  }
})

# 변경 후
configuration_values = jsonencode({
  env = {
    ENABLE_PREFIX_DELEGATION = "true"
    WARM_PREFIX_TARGET       = "1"
  }
  enableNetworkPolicy = "true"          # ← 루트 레벨로 이동
})
```
