## 2. 노드 장애 원인 (ip-10-10-12-254)

### 증상

```
23:00:18 KST  kubelet이 API Server에 status 보고를 중단
23:05:19 KST  node-controller: NodeStatusUnknown 전환
              node.kubernetes.io/unreachable:NoExecute taint 자동 부여
              karpenter.sh/disrupted:NoSchedule taint 추가 (Karpenter)
```

### 원인 분석

해당 노드는 생성 후 5시간 50분이 경과한 상태였다. kubelet이 멈춘 정확한 원인은 클러스터 외부(EC2 레이어)에 있으며, 가능성은 다음과 같다.

| 가능성 | 설명 |
|--------|------|
| Karpenter 선제 종료 중 중단 | 이전 pod 처리 완료 → WhenEmpty 정책으로 Karpenter가 EC2 Terminate 시작 → 종료 중인 EC2에서 kubelet이 응답 중단. **가장 유력** |
| GPU 드라이버 크래시 | NVIDIA 드라이버 패닉 시 kubelet 연쇄 중단 |
| 노드 OOM | 모델 로딩 중 메모리 초과 → OS 레벨 kill |
| EC2 하드웨어 이슈 | AWS 인프라 레벨 장애 |

**Karpenter 선제 종료 시나리오**: GPU NodePool은 `consolidationPolicy: WhenEmpty`, `consolidateAfter: 5m`로 설정되어 있다. 이전 pod 처리가 끝난 뒤 5분 후 Karpenter가 EC2 종료를 시작했고, EC2가 종료 과정에 있는 동안 KEDA가 새 SQS 메시지를 감지해 `jzmbn` pod를 죽어가는 노드에 스케줄했을 가능성이 높다.

EC2 시스템 로그 조회로 원인 확정 가능:

```bash
aws ec2 get-console-output \
  --instance-id <instance-id> \
  --region ap-northeast-2
```

### 자동 복구 흐름

```
kubelet 중단
  → node-controller: unreachable:NoExecute taint 부여
  → TaintManagerEviction: pod jzmbn 강제 축출 시작 (Terminating)
  → Karpenter: disrupted:NoSchedule 추가, 노드 삭제 시도
  → "DisruptionBlocked: pod 아직 Terminating 중"
  → jzmbn 종료 완료 → Karpenter가 EC2 인스턴스 삭제
```

**수동 개입 불필요.** pod Terminating이 완료되면 Karpenter가 자동으로 NotReady 노드를 회수한다.

## 3. scaleOnInFlight 동작과 다중 노드 생성

### scaleOnInFlight 개념

KEDA의 `scaleOnInFlight: "true"` 설정은 SQS 큐의 **in-flight 메시지(worker가 수신했지만 아직 DeleteMessage를 보내지 않은 메시지)**를 스케일링 판단에 포함시킨다.

```
SQS 메시지 상태:
  Visible    → 아직 어떤 worker도 수신하지 않은 상태 (일반적인 큐 길이)
  In-flight  → worker가 ReceiveMessage했지만 처리 미완료 상태
               visibility_timeout 동안 다른 worker에게 안 보임

scaleOnInFlight=false (기본):  visible 메시지만 카운트
scaleOnInFlight=true  (현재):  visible + in-flight 합산하여 카운트
```

**정상 동작 예시**:

```
메시지 도착 (visible=1)   → KEDA: 1개 필요 → scale 1
worker 수신 (in-flight=1) → KEDA: in-flight 1개 카운트 → scale 유지
처리 완료, DeleteMessage  → KEDA: 0 → scale 0 (cooldown 후)
```

### 오늘 발생한 이상 동작 (연쇄 재스케줄링)

```
① ip-10-10-12-254 노드 장애
   → pod jzmbn 축출 (Terminating 시작, grace 300s)
   → SQS 메시지 처리 미완료 → visibility_timeout(1800s) 만료까지 in-flight 유지

② KEDA가 일시적으로 in-flight 카운트를 0으로 읽음
   → KEDAScaleTargetDeactivated (replicas: 1 → 0)
   → pod들 Terminating 시작

③ KEDA 다음 폴링 주기에 in-flight 메시지 재감지
   → 즉시 reactivate (replicas: 0 → 1)
   → 새 pod 필요

④ 스케줄러: 새 pod를 올릴 노드 탐색
   → 기존 노드들은 Terminating pod가 GPU(nvidia.com/gpu: 1) 점유 중
     ※ Terminating 상태에서도 리소스를 반환하지 않음 (grace period 동안)
   → Karpenter: 새 노드 프로비저닝
   → ip-10-10-12-218 생성 → jg7ws 스케줄

⑤ KEDA: 큐 상태 재폴링 → deactivated → jg7ws도 Terminating 시작
   → ③~④ 반복 → ip-10-10-11-11, ip-10-10-12-47 추가 프로비저닝
```

### 시각화

```
시간 →
pod  jzmbn  [====처리중====][==========Terminating 300s==========]
pod  jg7ws                       [짧게실행][Terminating]
pod  lqlpm                                    [짧게실행][Terminating]

node 254    [======5h50m======][X 장애]
node 218                            [프로비저닝][Ready]
node 11-11                                     [프로비저닝][Ready]
node 47                                                   [프로비저닝][Ready] ← pod 없음
```

### 핵심 원인 조합

| 요인 | 역할 |
|------|------|
| `terminationGracePeriodSeconds: 300` | Terminating pod가 5분간 GPU 리소스를 점유 |
| `scaleOnInFlight: "true"` | 큐가 비어 보여도 in-flight 감지 시 즉시 재활성화 |
| KEDA 폴링 간격 | 짧은 주기로 activate/deactivate 반복 |
| Karpenter WhenEmpty 정책 | 각 사이클마다 새 노드 프로비저닝 |

## 4. On-Demand G/VT 인스턴스 vCPU 한도 32 영향

### 변경 내용

AWS Service Quota "Running On-Demand G and VT instances" 를 상향 조정했다.

```
변경 전: 4 vCPU  → g4dn.xlarge(4 vCPU) 1대만 동시 실행 가능
변경 후: 32 vCPU → g4dn.xlarge 최대 8대 동시 실행 가능
```

Karpenter GPU NodePool도 동일한 상한을 갖는다:

```yaml
# k8s/platform/karpenter/base/nodepools.yaml
limits:
  cpu: "32"      # g4dn.xlarge(4 vCPU) × 최대 8대
  memory: "128Gi"
```

### 실제 영향

| 영향 | 내용 |
|------|------|
| **긍정적** | GPU 노드 장애 시 즉시 새 노드로 재스케줄 가능 |
| **긍정적** | 향후 복수 분석 요청 병렬 처리 가능 (현재 maxReplica=1이라 미사용) |
| **주의** | 오늘처럼 노드 장애 + scaleOnInFlight 조합 시 비의도적 다중 노드 프로비저닝 가능 |

**콜드 스타트 해결 여부 (쿼터 관점)**: 해결 안 됨. 쿼터는 "몇 대까지"의 상한이며 "얼마나 빨리" 뜨는지와 무관하다.
> **추가 (2026-06-19)**: 콜드 스타트 자체는 EFS 모델 캐싱을 통해 별도 해결됨 (5~10분 → 3~5분). docs/shared/gpu-cold-start-strategy.md 참고.

**오늘 사례**: 쿼터 증가 전이었다면 2번째 노드 프로비저닝에서 quota 초과로 실패하고 pod가 Pending 상태로 대기했을 것이다. 쿼터 증가로 인해 4대까지 프로비저닝이 진행됐다.

## 6. KEDA 무한 루프 — GPU 노드가 사라지지 않는 현상

위 노드 장애가 정리된 이후에도 GPU 노드가 계속 새로 생성되고 죽는 현상이 반복됐다.  
사용자 요청이 전혀 없는 상태였음에도 10분 주기로 KEDA가 activate → 노드 생성 → 노드 NotReady → 반복.

### 관찰된 패턴

```
[~10분 주기 반복]

KEDA activate → pod 생성 → 노드 프로비저닝
                 → pod가 이미지 pull + 기동 직후 KEDA deactivate (SIGTERM)
                 → pod Terminating (grace 300s)
                 → 노드 NotReady (kubelet 사망, SIGKILL 미발송)
                 → pod 영원히 stuck Terminating
                 → 약 10분 후 KEDA 다시 activate → 반복
```

관찰된 노드 수명:

```
ip-10-10-12-254   5h50m 후 NotReady
ip-10-10-11-199   ~16m 후 NotReady
ip-10-10-12-248   ~12m 후 NotReady
```

### 근본 원인: AI 코드의 VisibilityTimeout 하드코딩

**`UtterAI_AI/app/workers/ml_gpu_worker.py`**

```python
response = sqs.receive_message(
    QueueUrl=queue_url,
    VisibilityTimeout=600,   # ← 이 줄이 문제
    ...
)
```

Terraform에서 `gpu-inference-queue`의 기본 VisibilityTimeout을 1800s로 상향했지만,  
worker 코드가 `receive_message()` 호출 시 `VisibilityTimeout=600`을 명시해서 **큐 기본값을 무시하고 600s로 덮어씌운다.**

#### 실제 동작 흐름

```
t=0s      worker가 SQS 메시지 수신 (VisibilityTimeout=600 적용)
           → 메시지 NotVisible 상태, 600s 타이머 시작

t=0~수초  KEDA: SQS 재폴링 결과 visible=0 → deactivate
           → pod SIGTERM

t=수초~   pod Terminating (grace 300s) 중 노드 NotReady
           → kubelet 사망 → SIGKILL 미발송 → pod stuck
           → worker 프로세스 종료, DeleteMessage 호출 안 됨

t=600s    VisibilityTimeout 만료 → 메시지 다시 visible
           → KEDA 감지, activate → 새 노드 프로비저닝 → 처음으로

[이 사이클이 영원히 반복]
```

`receive_message(VisibilityTimeout=600)` 파라미터가 없었다면 큐 기본값(1800s)이 적용되어  
적어도 30분 주기로 느려지고, 노드 장애가 해소되면 자연 복구됐을 것이다.  
600s 하드코딩이 10분마다 재등장을 보장하면서 무한 루프가 만들어진 것이다.

#### SQS 조회가 0을 보여주는 이유

점검 시점에 SQS가 `ApproximateNumberOfMessages: 0`, `ApproximateNumberOfMessagesNotVisible: 0`을 반환했다.  
이는 메시지가 없는 게 아니라, worker가 다시 메시지를 수신해서 NotVisible 상태로 전환된 직후에 조회했거나,  
SQS의 `Approximate` 특성상 수초 지연으로 0이 나타난 것이다. 실제 메시지는 큐에 존재했다.

### 긴급 조치 전체 절차 (완료)

#### 1차 시도: purge → 실패

```bash
kubectl delete pod utterai-ml-gpu-worker-6c8c885d7-ck5vl \
  -n utterai-ai-gpu --force --grace-period=0

aws sqs purge-queue \
  --queue-url "https://sqs.ap-northeast-2.amazonaws.com/032886669461/utterai-dev-gpu-inference-queue" \
  --region ap-northeast-2
```

**결과**: purge 실행 시점에 메시지가 이미 in-flight(NotVisible) 상태였다. purge는 **visible 메시지만 삭제**하므로 해당 메시지를 잡지 못했다. 600s 후 메시지가 다시 visible이 되면서 KEDA가 재활성화됐다.

추가 제약: SQS purge는 실행 후 **60초 동안 재실행 불가** (AWS 제한). 타이밍을 맞춰 재시도해도 in-flight 메시지는 여전히 잡을 수 없다.

#### 2차 시도: KEDA pause + 직접 삭제 → 성공

purge만으로는 in-flight 메시지를 잡을 수 없기 때문에, KEDA를 먼저 pause해서 사이클 자체를 끊은 뒤 메시지가 visible이 될 때 잡는 방식으로 전환했다.

**KEDA pause 방법**

ScaledObject에 어노테이션을 부여하면 KEDA가 SQS를 감지해도 scale up을 실행하지 않는다.

```bash
# pause: 큐에 메시지가 있어도 pod를 만들지 않음
kubectl annotate scaledobject utterai-ml-gpu-worker-scaledobject \
  -n utterai-ai-gpu \
  autoscaling.keda.sh/paused-replicas="0" --overwrite

# pause 해제
kubectl annotate scaledobject utterai-ml-gpu-worker-scaledobject \
  -n utterai-ai-gpu \
  autoscaling.keda.sh/paused-replicas- --overwrite
```

**전체 순서**

```bash
# 1. KEDA pause → 이후 메시지가 visible이 돼도 pod 생성 안 함
kubectl annotate scaledobject utterai-ml-gpu-worker-scaledobject \
  -n utterai-ai-gpu autoscaling.keda.sh/paused-replicas="0" --overwrite

# 2. stuck pod 전부 강제 삭제
kubectl delete pod -n utterai-ai-gpu --all --force --grace-period=0

# 3. 메시지가 visible이 되길 기다렸다가 receive + delete
#    (visible 상태일 때만 ReceiveMessage로 잡을 수 있음)
QUEUE_URL="https://sqs.ap-northeast-2.amazonaws.com/032886669461/utterai-dev-gpu-inference-queue"
MSGS=$(aws sqs receive-message --queue-url "$QUEUE_URL" \
  --max-number-of-messages 10 --region ap-northeast-2 --output json)
# ReceiptHandle로 직접 삭제

# 4. DLQ도 확인 후 purge
aws sqs purge-queue \
  --queue-url "https://sqs.ap-northeast-2.amazonaws.com/032886669461/utterai-dev-gpu-inference-dlq" \
  --region ap-northeast-2

# 5. KEDA pause 해제
kubectl annotate scaledobject utterai-ml-gpu-worker-scaledobject \
  -n utterai-ai-gpu autoscaling.keda.sh/paused-replicas- --overwrite
```

**결과**: 메인 큐, DLQ 모두 0 확인. KEDA `ScalerNotActive` 유지.

#### KEDA pause 해제 직후 pod 1회 기동

pause 어노테이션을 제거하면 KEDA가 스케일러를 재빌드(`KEDAScalersStarted`)하면서 **첫 폴링에 1회 activate**되는 현상이 발생했다. pod가 기동됐다가 즉시 SIGTERM을 받고 Terminating으로 전환됐다. SQS는 0을 유지했고 이후 재활성화 없이 안정됐다.

이미지가 노드에 캐시된 상태(`already present on machine`)였으므로 새 노드 프로비저닝 없이 기존 노드에서 즉시 실행됐다가 종료됐다. 이 pod Terminating 완료 후 노드도 WhenEmpty 정책으로 자동 회수됐다.

### AI 팀 수정 사항 (완료)

**`UtterAI_AI/app/workers/ml_gpu_worker.py`**

```python
# 수정 전
response = sqs.receive_message(
    QueueUrl=queue_url,
    VisibilityTimeout=600,   # 제거
    ...
)

# 수정 후
response = sqs.receive_message(
    QueueUrl=queue_url,
    # VisibilityTimeout 미지정 → 큐 기본값(1800s) 적용
    ...
)
```

이 파라미터를 제거하면 큐 기본값 1800s가 적용된다.  
이미 처리 중인 메시지의 timeout 연장(heartbeat)도 함께 구현하면 완전한 해결이 된다.  
(heartbeat 패턴은 2026-06-18 트러블슈팅 7번 항목 참고)

## 8. ArgoCD selfHeal — KEDA 스케일 제어 충돌로 인한 GPU Pod flapping

### 증상

GPU pod가 요청 없이도 계속 떴다가 죽는 현상. ArgoCD에서 `utterai-ml-gpu-worker` Deployment가 OutOfSync로 표시됨.

### 원인

`selfHeal: true`인 ArgoCD Application과 KEDA ScaledObject의 `minReplicaCount: 0` 충돌.

```
KEDA: SQS 큐 비어있음 → Deployment replicas=0 → Pod 종료
ArgoCD selfHeal: Git은 replicas=1 → 강제 1로 복구 → Pod 생성
KEDA: 여전히 큐 비어있음 → replicas=0 → Pod 종료
(무한 반복)
```

`ml-gpu-worker-deployment.yaml`의 `spec.replicas: 1`이 Git 기준값으로 존재하는 한,
ArgoCD는 KEDA가 변경한 replicas를 항상 drift로 감지해 복구를 시도한다.

### 해결

`deploy/argocd/dev/ai-worker-dev.yaml`에 `ignoreDifferences` 추가 (PR #214):

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

ArgoCD가 `/spec/replicas` 차이를 OutOfSync로 판단하지 않으므로 selfHeal이 트리거되지 않는다.
KEDA는 여전히 SQS 기반으로 0↔1을 자유롭게 제어한다.

### 핵심 교훈

KEDA + ArgoCD `selfHeal: true` 조합에서는 반드시 `ignoreDifferences`로 `/spec/replicas`를 제외해야 한다.
이 설정 없이는 KEDA의 scale-to-zero가 ArgoCD에 의해 지속적으로 무효화된다.
batch-worker, cpu-worker의 ScaledObject도 동일 패턴이므로 Deployment 전체에 적용하는 것이 안전하다.

## 7. 핵심 교훈

1. **Terminating pod는 GPU 리소스를 grace period 동안 점유한다.** `terminationGracePeriodSeconds` 동안 새 pod가 동일 노드에 스케줄되지 못해 Karpenter가 새 노드를 프로비저닝한다.

2. **scaleOnInFlight는 안정성을 높이지만 노드 장애 상황에서는 rapid activate/deactivate 사이클을 유발할 수 있다.** in-flight 카운트 폴링 타이밍에 따라 KEDA가 짧은 시간 안에 여러 번 scale up 신호를 보낸다.

3. **vCPU 쿼터 증가는 재스케줄링 가용성을 높이는 동시에, 이상 동작 시 더 많은 노드가 프로비저닝될 수 있는 여지를 준다.** NodePool의 `limits.cpu`와 ScaledObject의 `maxReplicaCount`가 실질적인 상한 역할을 한다.

4. **WhenEmpty 정책의 GPU NodePool에서 Karpenter 종료와 KEDA 스케일업이 타이밍이 맞으면 죽어가는 노드에 새 pod가 스케줄될 수 있다.** 이 경우 노드 장애가 연쇄적으로 보일 수 있다.

5. **`receive_message()`의 `VisibilityTimeout` 파라미터는 큐 기본값을 덮어쓴다.** 인프라에서 아무리 큐 timeout을 늘려도 앱 코드에 하드코딩된 값이 있으면 실제로는 그 값이 적용된다. 인프라와 앱 코드를 함께 확인해야 한다.
