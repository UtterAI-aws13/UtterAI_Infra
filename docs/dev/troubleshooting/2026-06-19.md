## 2. 노드 장애 원인 (ip-10-10-12-254)

### 증상

```
23:00:18 KST  kubelet이 API Server에 status 보고를 중단
23:05:19 KST  node-controller: NodeStatusUnknown 전환
              node.kubernetes.io/unreachable:NoExecute taint 자동 부여
              karpenter.sh/disrupted:NoSchedule taint 추가 (Karpenter)
```

### 원인 분석

해당 노드는 생성 후 5시간 50분이 경과한 상태였다. kubelet이 멈춘 정확한 원인은 클러스터 외부(EC2 레이어)에 있으며, 가능성은 다음과 같다.

| 가능성 | 설명 |
|--------|------|
| Karpenter 선제 종료 중 중단 | 이전 pod 처리 완료 → WhenEmpty 정책으로 Karpenter가 EC2 Terminate 시작 → 종료 중인 EC2에서 kubelet이 응답 중단. **가장 유력** |
| GPU 드라이버 크래시 | NVIDIA 드라이버 패닉 시 kubelet 연쇄 중단 |
| 노드 OOM | 모델 로딩 중 메모리 초과 → OS 레벨 kill |
| EC2 하드웨어 이슈 | AWS 인프라 레벨 장애 |

**Karpenter 선제 종료 시나리오**: GPU NodePool은 `consolidationPolicy: WhenEmpty`, `consolidateAfter: 5m`로 설정되어 있다. 이전 pod 처리가 끝난 뒤 5분 후 Karpenter가 EC2 종료를 시작했고, EC2가 종료 과정에 있는 동안 KEDA가 새 SQS 메시지를 감지해 `jzmbn` pod를 죽어가는 노드에 스케줄했을 가능성이 높다.

EC2 시스템 로그 조회로 원인 확정 가능:

```bash
aws ec2 get-console-output \
  --instance-id <instance-id> \
  --region ap-northeast-2
```

### 자동 복구 흐름

```
kubelet 중단
  → node-controller: unreachable:NoExecute taint 부여
  → TaintManagerEviction: pod jzmbn 강제 축출 시작 (Terminating)
  → Karpenter: disrupted:NoSchedule 추가, 노드 삭제 시도
  → "DisruptionBlocked: pod 아직 Terminating 중"
  → jzmbn 종료 완료 → Karpenter가 EC2 인스턴스 삭제
```

**수동 개입 불필요.** pod Terminating이 완료되면 Karpenter가 자동으로 NotReady 노드를 회수한다.

## 3. scaleOnInFlight 동작과 다중 노드 생성

### scaleOnInFlight 개념

KEDA의 `scaleOnInFlight: "true"` 설정은 SQS 큐의 **in-flight 메시지(worker가 수신했지만 아직 DeleteMessage를 보내지 않은 메시지)**를 스케일링 판단에 포함시킨다.

```
SQS 메시지 상태:
  Visible    → 아직 어떤 worker도 수신하지 않은 상태 (일반적인 큐 길이)
  In-flight  → worker가 ReceiveMessage했지만 처리 미완료 상태
               visibility_timeout 동안 다른 worker에게 안 보임

scaleOnInFlight=false (기본):  visible 메시지만 카운트
scaleOnInFlight=true  (현재):  visible + in-flight 합산하여 카운트
```

**정상 동작 예시**:

```
메시지 도착 (visible=1)   → KEDA: 1개 필요 → scale 1
worker 수신 (in-flight=1) → KEDA: in-flight 1개 카운트 → scale 유지
처리 완료, DeleteMessage  → KEDA: 0 → scale 0 (cooldown 후)
```

### 오늘 발생한 이상 동작 (연쇄 재스케줄링)

```
① ip-10-10-12-254 노드 장애
   → pod jzmbn 축출 (Terminating 시작, grace 300s)
   → SQS 메시지 처리 미완료 → visibility_timeout(1800s) 만료까지 in-flight 유지

② KEDA가 일시적으로 in-flight 카운트를 0으로 읽음
   → KEDAScaleTargetDeactivated (replicas: 1 → 0)
   → pod들 Terminating 시작

③ KEDA 다음 폴링 주기에 in-flight 메시지 재감지
   → 즉시 reactivate (replicas: 0 → 1)
   → 새 pod 필요

④ 스케줄러: 새 pod를 올릴 노드 탐색
   → 기존 노드들은 Terminating pod가 GPU(nvidia.com/gpu: 1) 점유 중
     ※ Terminating 상태에서도 리소스를 반환하지 않음 (grace period 동안)
   → Karpenter: 새 노드 프로비저닝
   → ip-10-10-12-218 생성 → jg7ws 스케줄

⑤ KEDA: 큐 상태 재폴링 → deactivated → jg7ws도 Terminating 시작
   → ③~④ 반복 → ip-10-10-11-11, ip-10-10-12-47 추가 프로비저닝
```

### 시각화

```
시간 →
pod  jzmbn  [====처리중====][==========Terminating 300s==========]
pod  jg7ws                       [짧게실행][Terminating]
pod  lqlpm                                    [짧게실행][Terminating]

node 254    [======5h50m======][X 장애]
node 218                            [프로비저닝][Ready]
node 11-11                                     [프로비저닝][Ready]
node 47                                                   [프로비저닝][Ready] ← pod 없음
```

### 핵심 원인 조합

| 요인 | 역할 |
|------|------|
| `terminationGracePeriodSeconds: 300` | Terminating pod가 5분간 GPU 리소스를 점유 |
| `scaleOnInFlight: "true"` | 큐가 비어 보여도 in-flight 감지 시 즉시 재활성화 |
| KEDA 폴링 간격 | 짧은 주기로 activate/deactivate 반복 |
| Karpenter WhenEmpty 정책 | 각 사이클마다 새 노드 프로비저닝 |

## 4. On-Demand G/VT 인스턴스 vCPU 한도 32 영향

### 변경 내용

AWS Service Quota "Running On-Demand G and VT instances" 를 상향 조정했다.

```
변경 전: 4 vCPU  → g4dn.xlarge(4 vCPU) 1대만 동시 실행 가능
변경 후: 32 vCPU → g4dn.xlarge 최대 8대 동시 실행 가능
```

Karpenter GPU NodePool도 동일한 상한을 갖는다:

```yaml
# k8s/platform/karpenter/base/nodepools.yaml
limits:
  cpu: "32"      # g4dn.xlarge(4 vCPU) × 최대 8대
  memory: "128Gi"
```

### 실제 영향

| 영향 | 내용 |
|------|------|
| **긍정적** | GPU 노드 장애 시 즉시 새 노드로 재스케줄 가능 |
| **긍정적** | 향후 복수 분석 요청 병렬 처리 가능 (현재 maxReplica=1이라 미사용) |
| **주의** | 오늘처럼 노드 장애 + scaleOnInFlight 조합 시 비의도적 다중 노드 프로비저닝 가능 |

**콜드 스타트 해결 여부**: 해결 안 됨. 쿼터는 "몇 대까지"의 상한이며 "얼마나 빨리" 뜨는지와 무관하다.

**오늘 사례**: 쿼터 증가 전이었다면 2번째 노드 프로비저닝에서 quota 초과로 실패하고 pod가 Pending 상태로 대기했을 것이다. 쿼터 증가로 인해 4대까지 프로비저닝이 진행됐다.

## 5. 자동 정리 흐름 (조치 불필요)

발견 시점 이후 클러스터는 자동으로 정상 상태로 복귀한다.

```
1. pod jzmbn/jg7ws/lqlpm Terminating 완료 (terminationGracePeriodSeconds=300)
2. ip-10-10-12-254 NotReady 노드: Karpenter가 EC2 삭제
3. ip-10-10-12-218, ip-10-10-11-11: WhenEmpty + consolidateAfter=5m 경과 후 회수
4. ip-10-10-12-47: pod 없음 → 즉시 WhenEmpty 대상 → 5분 내 회수
5. 결과: SQS 큐 비어있으므로 GPU 노드 0대, pod 0개로 수렴
```

확인 방법:

```bash
kubectl get nodes -l workload=ai-gpu
kubectl get pods -n utterai-ai-gpu
```

## 6. 핵심 교훈

1. **Terminating pod는 GPU 리소스를 grace period 동안 점유한다.** `terminationGracePeriodSeconds` 동안 새 pod가 동일 노드에 스케줄되지 못해 Karpenter가 새 노드를 프로비저닝한다.

2. **scaleOnInFlight는 안정성을 높이지만 노드 장애 상황에서는 rapid activate/deactivate 사이클을 유발할 수 있다.** in-flight 카운트 폴링 타이밍에 따라 KEDA가 짧은 시간 안에 여러 번 scale up 신호를 보낸다.

3. **vCPU 쿼터 증가는 재스케줄링 가용성을 높이는 동시에, 이상 동작 시 더 많은 노드가 프로비저닝될 수 있는 여지를 준다.** NodePool의 `limits.cpu`와 ScaledObject의 `maxReplicaCount`가 실질적인 상한 역할을 한다.

4. **WhenEmpty 정책의 GPU NodePool에서 Karpenter 종료와 KEDA 스케일업이 타이밍이 맞으면 죽어가는 노드에 새 pod가 스케줄될 수 있다.** 이 경우 노드 장애가 연쇄적으로 보일 수 있다.
