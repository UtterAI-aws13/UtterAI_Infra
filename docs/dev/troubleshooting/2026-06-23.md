## 1. Backend Rolling Update 교착 — maxSurge: 0 미설정

### 1-1. 발견된 상태

prod backend rolling update 시 새 pod가 Pending 상태에서 멈추고 배포가 완료되지 않음.

```
pod/utterai-api-green-xxx   0/1   Pending   0   5m
```

Karpenter 로그:
```
unable to schedule pod ... no matching NodePool found
```

### 1-2. 원인 분석

prod backend는 `requiredDuringSchedulingIgnoredDuringExecution` anti-affinity로 pod마다 별도 노드를 요구한다. replicas=2, 노드=2인 상태에서 기본 `maxSurge: 1`이 적용되면 rolling update 중 3번째 pod가 추가로 필요해진다.

Karpenter는 이 일시적 3번째 pod를 위한 노드를 NodePool 조건에 맞게 프로비저닝하지 못했고(GPU NodePool과 충돌), pod가 무한 Pending.

```
replicas=2, 노드=2 → maxSurge=1 → 순간 3개 pod 필요 → 3번째 노드 필요
→ Karpenter 프로비저닝 실패 → Pending 교착
```

### 1-3. 해결

`k8s/apps/backend/overlays/prod/patch-deployment.yaml`에 rolling update 전략 명시 (PR #282):

```yaml
strategy:
  rollingUpdate:
    maxSurge: 0
    maxUnavailable: 1
```

`maxSurge: 0`으로 기존 pod를 먼저 종료한 후 새 pod를 스케줄링하므로, 동시 최대 pod 수가 replicas를 초과하지 않는다.

### 1-4. 핵심 교훈

anti-affinity로 pod마다 전용 노드를 요구하는 구조에서는 `maxSurge: 0, maxUnavailable: 1`이 기본값이어야 한다. 노드 수 = replicas 조건에서 `maxSurge > 0`이면 rolling update가 반드시 막힌다.

## 2. readOnlyRootFilesystem 일괄 적용 — /tmp emptyDir 마운트

### 2-1. 배경

prod 보안 강화 항목으로 모든 워크로드에 `readOnlyRootFilesystem: true` 적용. backend blue/green, cpu-worker, ml-gpu-worker, batch-worker 대상.

### 2-2. 변경 사항

`k8s/apps/backend/overlays/prod/patch-deployment.yaml`,  
`k8s/apps/ai-worker/overlays/prod/patch-deployment.yaml` (PR #280):

```yaml
securityContext:
  readOnlyRootFilesystem: true

volumes:
  - name: tmp
    emptyDir: {}

volumeMounts:
  - name: tmp
    mountPath: /tmp
```

AI worker에는 추가로:

```yaml
env:
  - name: HF_HOME
    value: /tmp/huggingface
```

### 2-3. 후속 이슈

HF_HOME을 `/tmp/huggingface`로 설정했으나, pyannote 라이브러리가 `/home/appuser/.cache`를 직접 사용하는 코드 경로가 남아 있어 다음날(2026-06-24) 추가 수정 필요. → [2026-06-24 #1 참조]

## 3. IRSA trust policy namespace 하드코딩 — dev pod AssumeRole 실패

### 3-1. 발견된 상태

dev API pod가 S3 요청에서 403 에러 반환:

```
AccessDenied: User: arn:aws:sts::032886669461:assumed-role/utterai-dev-api-irsa-role/...
is not authorized to perform: sts:AssumeRoleWithWebIdentity
```

### 3-2. 원인 분석

`terraform/modules/irsa/main.tf`의 API IRSA trust policy:

```hcl
# 수정 전 — namespace 하드코딩
"${local.oidc_sub}" = "system:serviceaccount:utterai-prod-api:utterai-api-sa"
```

prod namespace(`utterai-prod-api`)가 하드코딩되어 있어 dev namespace(`utterai-api`)에서 실행 중인 pod의 OIDC token sub claim과 불일치. dev pod는 AssumeRoleWithWebIdentity를 전부 거부당함.

### 3-3. 해결

`terraform/modules/irsa/variables.tf`에 `api_namespace` 변수 추가, 환경별로 주입 (PR #287):

```hcl
# terraform/modules/irsa/main.tf
"${local.oidc_sub}" = "system:serviceaccount:${var.api_namespace}:utterai-api-sa"
```

```hcl
# dev/03-services/main.tf
api_namespace = "utterai-api"

# prod/03-services/main.tf
api_namespace = "utterai-prod-api"
```

### 3-4. 핵심 교훈

IRSA trust policy에서 namespace를 하드코딩하는 패턴은 dev/prod 분리 구조에서 반드시 깨진다. 모듈 작성 시 namespace를 변수로 받도록 강제해야 한다.

## 4. VPC Endpoint SG — Pod CIDR 미포함으로 SQS 통신 불가

### 4-1. 발견된 상태

dev에서 분석 작업 생성 시 15초 후 프론트엔드 타임아웃. 실제 SQS 메시지는 전송되지 않고 pod가 무응답 상태.

```
# SQS Interface Endpoint 요청이 응답 없이 멈춤
# ALB access log — API 요청 수신 후 응답 없음
```

### 4-2. 원인 분석

EKS VPC CNI prefix delegation이 활성화되면 pod IP는 secondary CIDR(`100.64.0.0/16`)에서 할당된다. VPC Endpoint 보안 그룹의 ingress rule은 VPC CIDR(`10.0.0.0/16`)만 허용했기 때문에, pod → SQS Interface Endpoint 443 트래픽이 SG에서 차단됨.

```hcl
# 수정 전
cidr_blocks = [var.vpc_cidr]  # 10.0.0.0/16만 허용

# pod IP는 100.64.0.0/16 → SG 차단 → 연결 없음
```

### 4-3. 해결

`terraform/modules/vpc/main.tf` VPC endpoint SG ingress 수정 (PR #287):

```hcl
# 수정 후
cidr_blocks = var.pod_cidr != null ? [var.vpc_cidr, var.pod_cidr] : [var.vpc_cidr]
```

dev 환경에서 `pod_cidr = "100.64.0.0/16"` 전달.

### 4-4. 핵심 교훈

EKS CNI prefix delegation 환경에서 VPC Endpoint SG는 VPC CIDR와 Pod CIDR를 모두 허용해야 한다. SQS/ECR/Secrets Manager 등 Interface Endpoint를 사용하는 모든 서비스에 동일하게 적용.

## 5. Kubecost Federated Storage — 3단계 연쇄 수정

Kubecost S3 federated storage 설정이 세 번의 커밋을 거쳐 수정됐다.

### 5-1. 1차: Thanos objectStore → federatedStorageConfig 변경 (PR #288)

**문제**: `kubecostModel.federatedStorageConfig`를 `thanos.objectStoreConfig`로 잘못 설정.

```hcl
# 수정 전 — 잘못된 설정 경로
federatedStorageConfig = {
  enabled             = true
  storageConfigSecret = "kubecost-federated-storage"
}
```

Kubecost 1.108+에서는 `kubecostModel.federatedStorageConfigSecret`을 사용해야 한다.

```hcl
# 수정 후
kubecostModel = {
  federatedStorageConfigSecret = "kubecost-federated-storage"
}
```

### 5-2. 2차: Secret 키 이름 및 포맷 수정 (PR #288)

**문제**: Secret의 `object-store.yaml` 키를 `yamlencode()`로 생성하면 JSON 포맷으로 직렬화되어 Kubecost가 파싱 실패.

```hcl
# 수정 전 — yamlencode는 JSON 포맷 출력
"object-store.yaml" = yamlencode({ type = "S3" ... })

# 수정 후 — heredoc으로 YAML 직접 작성, 키 이름도 federated-store.yaml
"federated-store.yaml" = <<-EOT
  type: S3
  config:
    bucket: ${var.kubecost_s3_bucket_name}
    endpoint: s3.${var.aws_region}.amazonaws.com
    region: ${var.aws_region}
EOT
```

### 5-3. 3차: IRSA에 EC2/Pricing 권한 추가 (PR #291)

**문제**: Kubecost가 비용 데이터 수집을 위해 필요한 EC2/Pricing API 권한이 IRSA 정책에 없었음.

```hcl
# 추가된 권한
Action = [
  "ec2:DescribeAddresses",
  "ec2:DescribeInstances",
  "ec2:DescribeRegions",
  "ec2:DescribeSnapshots",
  "ec2:DescribeVolumes",
  "ec2:DescribeVolumesModifications",
  "ec2:DescribeVolumeStatus",
  "pricing:GetProducts"
]
Resource = "*"
```

### 5-4. 핵심 교훈

- `yamlencode()`는 JSON을 출력한다. YAML 포맷이 필요한 K8s Secret 값은 heredoc으로 직접 작성해야 한다.
- Kubecost federated storage 설정 경로는 버전마다 다르다. 공식 문서에서 `kubecostModel.federatedStorageConfigSecret` 경로를 확인하고 적용해야 한다.
- Secret 키 이름(`object-store.yaml` vs `federated-store.yaml`)은 Kubecost 버전에 따라 다르다. Helm values 문서 확인 필수.

## 6. dev S3 Bucket Env Var 이름 변경 — BE PR #74 대응

### 6-1. 발견된 상태

dev API에서 S3 presigned URL 생성 실패. 업로드 버튼 클릭 시 에러 반환.

### 6-2. 원인 분석

BE PR #74에서 S3 bucket 환경변수 이름을 변경:

```
RAW_AUDIO_BUCKET     → S3_BUCKET_AUDIO
TEMPLATE_BUCKET      → S3_BUCKET_TEMPLATE
(S3_BUCKET_TRANSCRIPT 신규 추가)
```

`k8s-legacy/workloads/api-deployment.yaml`에서 여전히 구 이름을 사용해 BE가 버킷 이름을 읽지 못함.

### 6-3. 해결

`k8s-legacy/workloads/api-deployment.yaml` ConfigMap 수정 (PR #290):

```yaml
# 수정 전
RAW_AUDIO_BUCKET: "utterai-dev-raw-audio"
TEMPLATE_BUCKET: "utterai-dev-documents"

# 수정 후
S3_BUCKET_AUDIO: "utterai-dev-raw-audio"
S3_BUCKET_TEMPLATE: "utterai-dev-documents"
S3_BUCKET_TRANSCRIPT: "utterai-dev-transcripts"
```

### 6-4. 핵심 교훈

BE 환경변수 이름 변경 PR이 머지될 때 infra ConfigMap 변경도 동시에 반영해야 한다. BE PR이 dev에 먼저 배포되는 경우, infra에도 같은 날 연동 PR을 올리는 워크플로우가 필요.

## 7. AWS Client VPN — 인증서 기반 Private EKS Endpoint 접근

### 7-1. 배경

EKS API 서버가 private endpoint로만 노출되어 VPN 없이는 `kubectl` 사용 불가. 팀원 전원이 EKS 접근을 위해 Client VPN 필요.

### 7-2. 구성 내용 (PR #286, #289)

**인증서 기반 Client VPN**:

```hcl
# terraform/environments/prod/04-addons/main.tf
resource "aws_ec2_client_vpn_endpoint" "main" {
  client_cidr_block      = "10.100.0.0/16"
  server_certificate_arn = aws_acm_certificate.vpn_server.arn
  authentication_options {
    type                       = "certificate-authentication"
    root_certificate_chain_arn = aws_acm_certificate.vpn_client.arn
  }
}
```

**Split tunnel 활성화** (PR #289):

```hcl
split_tunnel = true
```

Split tunnel OFF 상태에서는 모든 트래픽이 VPN을 통해 라우팅되어 인터넷 접속이 차단됨. Split tunnel ON으로 VPC 내부 트래픽만 VPN을 통하고 인터넷은 직접 접속.

### 7-3. 핵심 교훈

Client VPN은 기본적으로 split tunnel이 꺼져 있어 인터넷이 차단된다. 개발 환경에서는 반드시 `split_tunnel = true`로 설정해야 한다.

## 8. 핵심 교훈 종합

1. **anti-affinity + 노드 수 = replicas 구조에서는 `maxSurge: 0, maxUnavailable: 1`을 반드시 명시한다.** 기본 maxSurge: 1이 rolling update를 교착시킨다.

2. **EKS CNI prefix delegation 환경에서 VPC Endpoint SG는 Pod CIDR도 허용해야 한다.** Pod IP가 secondary CIDR에서 나오면 VPC CIDR만 허용한 SG에 막힌다.

3. **IRSA trust policy의 namespace는 모듈 변수로 받아야 한다.** 하드코딩하면 dev/prod 전환 시 반드시 깨진다.

4. **`yamlencode()`는 JSON을 출력한다.** YAML 포맷이 필요한 Secret 값은 heredoc을 사용한다.

5. **BE 환경변수 이름이 변경되면 infra ConfigMap을 같은 날 업데이트해야 한다.** 특히 k8s-legacy와 k8s/ Kustomize overlay가 별도로 존재할 경우 둘 다 확인한다.

6. **Client VPN은 `split_tunnel = true`가 기본이어야 한다.** 끄면 인터넷이 막힌다.
