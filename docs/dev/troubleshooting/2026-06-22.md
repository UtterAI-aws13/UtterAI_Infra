# Troubleshooting — 2026-06-22

Prod 초기 운영 중 발생한 IRSA namespace 불일치로 인한 S3 500 에러, CORS 차단, ArgoCD-KEDA 충돌, S3 CORS validation 누락, CloudFront→ALB HTTPS 미설정 기록.

## 1. IRSA trust policy namespace 불일치 → prod API S3 전면 500

### 1-1. 발견된 상태

prod 배포 직후 API 전체에서 S3 관련 요청이 500 에러를 반환.

```
AccessDenied: User: arn:aws:sts::032886669461:assumed-role/utterai-prod-api-irsa-role/...
is not authorized to perform: sts:AssumeRoleWithWebIdentity
```

pod가 IRSA 역할을 assume하지 못해 S3 서명 자체가 실패하는 상태.

### 1-2. 원인 분석

`utterai-prod-api-irsa-role`의 trust policy condition:

```json
{
  "StringEquals": {
    "oidc.eks.ap-northeast-2.amazonaws.com/.../oidc/token:sub":
      "system:serviceaccount:utterai-api:utterai-api-sa"
  }
}
```

trust policy에 박힌 namespace가 `utterai-api` (dev namespace)로 설정되어 있었다.
prod 클러스터의 실제 namespace는 `utterai-prod-api`이므로 OIDC token의 sub claim과 일치하지 않아
`AssumeRoleWithWebIdentity`가 전부 거부됐다.

**원인**: `terraform/modules/irsa/main.tf`에서 namespace를 하드코딩했는데 dev 값이 그대로 복사된 것.

### 1-3. 해결

`terraform/modules/irsa/main.tf` trust policy 수정 (PR #267):

```hcl
# 수정 전
"${local.oidc_sub}" = "system:serviceaccount:utterai-api:utterai-api-sa"

# 수정 후
"${local.oidc_sub}" = "system:serviceaccount:utterai-prod-api:utterai-api-sa"
```

```bash
cd terraform/environments/prod/02-eks && terraform apply
# IAM 역할 trust policy 즉시 반영 → pod 재시작 불필요
```

### 1-4. 핵심 교훈

IRSA trust policy는 IAM Console에서 `utterai-prod-api-irsa-role` → `Trust relationships`를 확인하면 sub claim 값을 바로 볼 수 있다. S3 500이 전면 발생할 때 CloudWatch Logs 이전에 IRSA부터 확인하는 것이 빠르다.

## 2. Backend CORS — app.utterai.org 미포함으로 프론트엔드 API 차단

### 2-1. 발견된 상태

`https://app.utterai.org`에서 API 호출 시 CORS 에러:

```
Access to fetch at 'https://api.utterai.org/api/v1/...' from origin 'https://app.utterai.org'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present.
```

### 2-2. 원인 분석

`k8s/apps/backend/overlays/prod/patch-configmap.yaml`의 CORS 설정:

```yaml
# 수정 전
FRONTEND_ORIGIN: "https://utterai.com"
CORS_ALLOW_ORIGINS: "https://utterai.com"
CORS_ORIGINS: '["https://utterai.com"]'
```

prod 초기 설정 시 `utterai.com`만 허용 목록에 포함됐고, 실제 서비스 도메인 `app.utterai.org`가 누락됐다.

### 2-3. 해결

CORS 허용 목록에 `app.utterai.org` 추가 (PR #266):

```yaml
# 수정 후
FRONTEND_ORIGIN: "https://app.utterai.org"
CORS_ALLOW_ORIGINS: "https://app.utterai.org,https://utterai.com"
CORS_ORIGINS: '["https://app.utterai.org","https://utterai.com"]'
```

ArgoCD sync → backend pod rolling restart → CORS 정상화 확인.

### 2-4. 핵심 교훈

CORS 허용 목록은 실제 사용자가 접근하는 모든 origin을 포함해야 한다. 도메인 구조가 `utterai.com` / `app.utterai.org` / `www.utterai.org` 등으로 분산된 경우, prod 초기 배포 시 체크리스트로 관리해야 누락을 막을 수 있다.

## 3. ArgoCD ↔ KEDA replica drift — prod ai-worker OutOfSync

### 3-1. 발견된 상태

ArgoCD `utterai-ai-worker-prod` Application이 지속적으로 OutOfSync 상태. KEDA가 큐를 보고 replicas를 조정할 때마다 ArgoCD가 drift를 감지해 selfHeal을 시도.

```
OutOfSync — spec.replicas: 0 (live) vs 1 (git)
```

### 3-2. 원인 분석

```
KEDA: SQS 큐 비어있음 → Deployment replicas=0 설정
ArgoCD selfHeal: Git 기준 replicas=1 → 강제 1로 복구
KEDA: 다음 폴링에서 다시 replicas=0 설정
(반복)
```

dev 환경에서는 `ignoreDifferences`로 `/spec/replicas`를 이미 제외했지만, prod ArgoCD Application에는 적용이 빠졌다.

### 3-3. 해결

`deploy/argocd/prod/ai-worker-prod.yaml`에 `ignoreDifferences` 추가 (PR #265):

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```

ArgoCD가 `/spec/replicas` 차이를 OutOfSync로 판단하지 않으므로 selfHeal이 멈추고
KEDA가 SQS 기반으로 0↔N을 자유롭게 제어한다.

### 3-4. 핵심 교훈

dev에서 설정을 추가할 때 prod와의 동기화를 함께 확인해야 한다. KEDA ScaledObject를 쓰는 모든 ArgoCD Application에는 `/spec/replicas` ignoreDifferences가 필수다.

## 4. S3 CORS — frontend_domain 빈 문자열로 인한 invalid AllowedOrigins

### 4-1. 발견된 상태

S3 presigned URL을 통한 브라우저 업로드가 조용히 실패하는 현상. 에러 메시지 없이 업로드가 차단됨.

### 4-2. 원인 분석

`terraform/modules/s3/` 모듈의 CORS 설정:

```hcl
allowed_origins = ["https://${var.frontend_domain}"]
```

`frontend_domain`이 빈 문자열(`""`)로 전달되면 생성되는 CORS rule:

```json
{
  "AllowedOrigins": ["https://"]
}
```

`https://`는 어떤 브라우저 origin과도 일치하지 않으므로 모든 presigned URL 업로드가 차단된다. 에러 응답이 없어서 업로드가 단순히 멈춘 것처럼 보인다.

### 4-3. 해결

`terraform/modules/s3/variables.tf`에 validation 추가 (PR #269):

```hcl
variable "frontend_domain" {
  type = string
  validation {
    condition     = var.frontend_domain != ""
    error_message = "frontend_domain must not be empty (e.g. app.utterai.org). Empty value generates invalid CORS origin 'https://'."
  }
}
```

이후 `terraform plan` 단계에서 빈 문자열 전달 시 즉시 오류 발생.

### 4-4. 핵심 교훈

S3 CORS 설정 오류는 `4xx/5xx`가 아니라 브라우저의 preflight `OPTIONS` 요청이 올바른 origin 헤더를 반환하지 못하는 방식으로 나타난다. `https://` 같은 잘못된 origin 패턴은 AWS가 거부하지 않고 그냥 적용되기 때문에, Terraform `validation` 블록으로 upstream에서 차단하는 것이 가장 효과적이다.

## 5. CloudFront → ALB origin 프로토콜 불일치 및 잘못된 origin 도메인

### 5-1. 발견된 상태

`https://app.utterai.org`에서 API 요청 시 간헐적 502 / 연결 오류. ALB access log에는 정상 요청이 기록되지만 CloudFront → API 응답이 불안정.

### 5-2. 원인 분석

`terraform/modules/cloudfront/main.tf`의 API origin 설정:

```hcl
# 수정 전
origin {
  domain_name = aws_lb.api.dns_name  # ALB의 내부 DNS
  origin_protocol_policy = "http-only"
}
```

두 가지 문제:
1. **프로토콜**: CloudFront → ALB 통신이 HTTP로 이루어져 ACM 인증서를 부착한 ALB에서 HTTPS redirect가 걸리는 상황에서 루프 발생 가능성
2. **origin domain**: ALB 내부 DNS 대신 `api.utterai.org`(Route 53 레코드)를 사용해야 ALB SG의 Host 헤더 기반 라우팅이 정상 동작

### 5-3. 해결

`terraform/modules/cloudfront/main.tf` origin 수정 (PR #260 포함):

```hcl
# 수정 후
origin {
  domain_name = "api.utterai.org"
  origin_protocol_policy = "https-only"
}
```

```bash
cd terraform/environments/prod/05-cloudfront && terraform apply
# CloudFront distribution update: 15~20분 전파 소요
```

### 5-4. 핵심 교훈

CloudFront origin에는 ALB의 내부 DNS(`xxx.elb.amazonaws.com`)보다 Route 53 레코드(`api.utterai.org`)를 사용하는 것이 Host 헤더 처리에 안전하다. ACM 인증서가 ALB에 붙어 있다면 origin 프로토콜은 `https-only`로 설정해야 한다.

## 6. Kubecost PVC — prod S3 storage 미설정으로 PVC 생성 실패

### 6-1. 발견된 상태

prod `04-addons` 배포 시 Kubecost PVC 생성 실패. prod 클러스터에는 Kubecost용 PV가 없는 상태.

### 6-2. 원인 분석

dev 환경의 Kubecost는 PVC를 사용하지만 prod에서는 S3 storage로 구성 예정이었다.
`terraform.tfvars`에 PVC 비활성화 설정이 반영되지 않아 prod에서도 PVC를 시도.

### 6-3. 해결

`terraform/environments/prod/04-addons/variables.tf` 및 `terraform.tfvars.example` 수정 (PR #245):

```hcl
# prod는 S3 storage 사용 → PVC 비활성화
kubecost_pvc_enabled = false
```

## 8. prod rag ingest secret 누락

### 8-1. 발견된 상태

prod RAG ingest worker가 DB 연결 실패. `utterai-prod-rag-ingest-secret`이 Secrets Manager에 존재하지 않음.

### 8-2. 원인 분석

dev에는 `secrets` 모듈에 rag ingest secret이 추가되어 있었지만, prod `03-services` 배포 시 해당 secret 리소스 정의가 누락됐다.

### 8-3. 해결

`terraform/modules/secrets/main.tf`에 rag ingest secret 리소스 추가, `terraform/environments/prod/03-services/main.tf`에서 호출 추가 (PR #240):

```hcl
resource "aws_secretsmanager_secret" "rag_ingest" {
  name = "${var.prefix}-rag-ingest-secret"
}
```

```bash
cd terraform/environments/prod/03-services && terraform apply
```

## 9. 핵심 교훈 종합

1. **IRSA trust policy는 namespace가 환경마다 다르다.** dev(`utterai-api`)와 prod(`utterai-prod-api`)를 구분해 각 환경에서 `terraform plan`으로 신규 배포 전 trust policy sub claim을 반드시 확인해야 한다. S3 500이 전면 발생하면 IRSA 상태를 먼저 확인한다.

2. **CORS 허용 목록은 실제 트래픽 origin을 모두 명시해야 한다.** 도메인 구조가 복잡할수록 초기 배포 체크리스트에 origin 목록 검증을 포함시켜야 한다. `app.utterai.org`와 `utterai.com`처럼 멀티 도메인 구조는 둘 다 명시한다.

3. **KEDA + ArgoCD selfHeal 조합에서 `/spec/replicas` ignoreDifferences는 prod에도 dev와 동일하게 적용해야 한다.** dev에서 설정을 추가할 때 prod 매니페스트와의 동기화를 PR 체크리스트에 포함시킨다.

4. **S3 CORS의 `frontend_domain` 같은 필수 문자열 변수는 Terraform `validation` 블록으로 빈 문자열을 차단해야 한다.** 빈 문자열이 조용히 통과하면 `https://`처럼 무의미한 값이 실제 AWS 리소스에 설정되고 에러 없이 운영에 영향을 준다.

5. **CloudFront → ALB origin은 `https-only` 프로토콜과 Route 53 레코드 도메인을 사용한다.** ALB 내부 DNS + `http-only` 조합은 ACM 인증서 환경에서 예측 불가능한 동작을 유발할 수 있다.

6. **dev에서 작동하는 secret/config가 prod에도 존재하는지 `03-services` 배포 직후 확인한다.** secret 누락은 pod 기동 후에야 발견되므로, terraform output에 secret ARN을 노출하고 배포 직후 AWS Console에서 존재 여부를 확인하는 것이 빠르다.
