## 1. ECR 이미지 push 후 API Pod 자동 교체 안 됨

### 증상
ECR에 새 이미지가 push됐는데 실행 중인 Pod가 교체되지 않음.

### 원인
Kubernetes는 ECR을 polling하지 않는다. `imagePullPolicy: Always`라도 Pod 자체가 재시작되지 않으면 새 이미지를 pull하지 않는다.
또한 ArgoCD는 Git 상태와 클러스터 상태를 동기화하므로, Git의 이미지 태그가 변경되지 않으면 Rollout이 발생하지 않는다.

### 현재 구조 (GitOps 정상 흐름)
```
ECR push (backend CI)
  → utterai-gitops-bot이 k8s/apps/backend/overlays/dev/kustomization.yaml 이미지 태그 자동 커밋
  → ArgoCD selfHeal 감지
  → Deployment Rollout
```

`kustomization.yaml`의 `newTag`가 변경되면 ArgoCD가 자동으로 Pod를 교체한다.

### 확인 방법
```bash
# 현재 실행 중인 Pod 이미지 확인
kubectl get pods -n utterai-dev -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[*].image}{"\n"}{end}'

# Image ID(sha256 digest)로 실제 빌드 확인
kubectl describe pod <pod-name> -n utterai-dev | grep -E "Image:|Image ID:"
```

## 2. Mixed Content — 브라우저가 ALB URL로 직접 요청

### 증상
```
Mixed Content: The page at 'https://d129p1nkqgquw3.cloudfront.net/dashboard' was loaded
over HTTPS, but requested an insecure XMLHttpRequest endpoint
'http://k8s-utteraidev-95adfecb1f-1669188398.ap-northeast-2.elb.amazonaws.com/api/v1/sessions/'.
This request has been blocked; the content must be served over HTTPS.
```

### 원인 파악 과정

1. S3 빌드 파일 확인 → `baseURL: "https://d129p1nkqgquw3.cloudfront.net/api/v1"` 정상
2. CloudFront 서빙 JS 확인 → 동일하게 정상
3. 서비스 워커 없음, LocalStorage 무관
4. CloudFront `/api/*` 프록시 정상 (`401 Unauthorized` 응답 확인)

**진짜 원인:**

```bash
# trailing slash 없는 경로 요청 시 307 리다이렉트 발생
curl -v "https://d129p1nkqgquw3.cloudfront.net/api/v1/sessions"
# → 307 Temporary Redirect
# → Location: http://k8s-utteraidev-95adfecb1f-1669188398.ap-northeast-2.elb.amazonaws.com/api/v1/sessions/

# trailing slash 있는 경로는 정상
curl -v "https://d129p1nkqgquw3.cloudfront.net/api/v1/sessions/"
# → 401 Unauthorized (정상)
```

FastAPI의 `redirect_slashes=True` (기본값)이 `/sessions` → `/sessions/` 로 307을 반환하는데,
Location 헤더에 ALB 자체 호스트명(`http://alb-url/...`)이 포함된다.
CloudFront는 이 307을 그대로 브라우저로 전달하고, 브라우저가 HTTP ALB URL을 직접 호출하려다 Mixed Content로 차단된다.

### 초기 대응 (잘못된 방향)
백엔드 `main.py`에 `redirect_slashes=False` 추가 → 307 자체를 없애는 방향으로 대응.

```python
app = FastAPI(redirect_slashes=False)
```

→ **이후 새 문제 발생. 섹션 3 참고.**

### 핵심 교훈
CloudFront → ALB 구간이 HTTP only이므로 FastAPI가 생성하는 307의 `Location` 헤더에 `http://alb-hostname/...` 절대 URL이 그대로 노출된다.
307 자체를 없애거나, Location을 상대 경로로 변환하거나, ALB에 HTTPS를 붙이는 세 가지 방법 중 하나로 대응해야 한다.

## 3. `redirect_slashes=False` 적용 후 프론트엔드 화면 전혀 안 뜸

### 증상
섹션 2의 `redirect_slashes=False` 적용 후 CloudFront URL 접속 시 화면이 아예 뜨지 않음.
브라우저 F12 콘솔에 다음 오류 출력:

```
TypeError: r.filter is not a function
    at q2 (index-BDva_e9H.js:240:113187)
    at gd (index-BDva_e9H.js:38:17007)
    ...
```

### 원인 분석

**FastAPI 0.116 라우트 변경 + `redirect_slashes=False` 조합이 문제였다.**

```
이전 상태 (정상):
  @router.get("")  →  실제 경로 /api/v1/sessions
  FE 요청 /api/v1/sessions → 200 ✅

FastAPI 0.116 호환성 수정 (PR #60):
  @router.get("/")  →  실제 경로 /api/v1/sessions/
  FE 요청 /api/v1/sessions → 307 → /api/v1/sessions/ ✅ (redirect_slashes=True 기본값)

redirect_slashes=False 추가 (PR #62):
  @router.get("/")  →  실제 경로 /api/v1/sessions/
  FE 요청 /api/v1/sessions → 404 ❌ (리다이렉트 없음)
```

FE `DashboardPage`의 `useEffect`에서 `sessionsApi.list()` 등이 404로 실패하는 것 자체는
`.catch()`로 처리되지만, 에러 응답 형태에 따라 `sessions` state가 비배열로 설정될 수 있다.
렌더 바디에서 `sessions.filter(...)` 호출 시 `TypeError`가 발생하고 React 렌더 트리 전체가 크래시한다.

FE가 호출하는 모든 list 엔드포인트(`/sessions`, `/patients`, `/analysis-jobs`, `/reports`)가
trailing slash 없이 요청하므로 전부 404 → 초기 렌더에 필요한 데이터가 하나도 없어 화면 불능.

### 해결

**인프라 (PR #163, `terraform/modules/cloudfront/main.tf`):**

CloudFront Function을 `/api/*` viewer-response에 연결해
FastAPI의 307 `Location` 헤더를 절대 URL에서 상대 경로로 변환.

```js
// http://alb-dns/api/v1/sessions/ → /api/v1/sessions/
function handler(event) {
  var response = event.response;
  var headers  = response.headers;

  if (headers.location) {
    var loc = headers.location.value;
    if (loc.indexOf('http://') === 0 || loc.indexOf('https://') === 0) {
      var afterProto = loc.indexOf('//') + 2;
      var pathStart  = loc.indexOf('/', afterProto);
      headers.location = { value: pathStart >= 0 ? loc.slice(pathStart) : '/' };
    }
  }

  return response;
}
```

브라우저는 상대 경로 Location을 현재 CloudFront HTTPS URL 기준으로 처리하므로
`https://cloudfront-url/api/v1/sessions/`로 리다이렉트된다.

**백엔드:**
`main.py`에서 `redirect_slashes=False` 제거 (`redirect_slashes=True` 기본값 복원).
307은 다시 발생하지만 CloudFront Function이 Location을 상대 경로로 변환해 mixed content 없음.

### 적용 순서

```
1. BE: redirect_slashes=False 제거 후 새 이미지 빌드·배포
2. Infra: PR #163 머지 후 04-addons terraform apply
```

### 핵심 교훈
- `redirect_slashes=False`는 307 문제를 없애지만, 라우트가 `"/"`로 정의된 경우
  trailing slash 없는 요청이 전부 404가 된다. FE가 모두 trailing slash 없이 호출한다면 치명적.
- CloudFront → ALB 구간의 307 mixed content는 인프라(CloudFront Function)에서 해결하는 것이 안전하다.
- FastAPI 버전 업으로 인한 라우트 경로 변경(`""` → `"/"`)은 기존 redirect 동작에 영향을 준다. 버전 업 시 반드시 확인.
