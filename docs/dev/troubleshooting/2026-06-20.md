## 3. 근본 원인 — Prefix Delegation + 서브넷 단편화

### Prefix Delegation 모드란

```bash
kubectl get daemonset aws-node -n kube-system \
  -o jsonpath='{...containers[?(@.name=="aws-node")].env[*]}'
# ENABLE_PREFIX_DELEGATION=true
# WARM_PREFIX_TARGET=1
```

`ENABLE_PREFIX_DELEGATION=true` 상태에서 IPAMD는 IP를 개별로 할당하는 것이 아니라 **/28 블록(16개 연속 IP)** 단위로 AWS에 요청한다.

```
일반 모드:  ENI에 IP 1개씩 할당 요청
PD 모드:    ENI에 /28 블록(16개 연속 IP) 할당 요청 → 1회 API 호출로 16개 확보
```

### 서브넷 단편화

```
10.10.11.0/24 (251 usable IPs)
  ↓ VPC Interface Endpoint 4개(SQS/SecretsManager/ECR-API/ECR-DKR)의 ENI
  ↓ 다수 노드의 Prefix Delegation warm pool 선점
  ↓ 단편화 진행

잔여 IP 112개 존재하지만
→ /28(16개) 정렬 블록이 하나도 없는 상태
→ AWS: InsufficientCidr 반환
→ IPAMD: 2분 대기 후 재시도 (영원히 반복)
```

노드에 파드가 5개뿐이고 `/24` 서브넷에 112개 IP가 남아도 Prefix Delegation은 **연속 16개 정렬 블록**을 요구하므로, 블록이 없으면 실패한다.

## 4. 해결 — Secondary CIDR 추가 및 Custom Networking 전환

### 설계

```
Before:
  노드 IP   → 10.10.11.x (primary 서브넷, 단편화됨)
  파드 IP   → 10.10.11.x (same, 단편화 심화)

After:
  노드 IP   → 10.10.11.x / 10.10.12.x (primary 서브넷 유지)
  파드 IP   → 100.64.x.x  (secondary CIDR 전용 서브넷, 32,766 IPs per AZ)
```

VPC에 `100.64.0.0/16` secondary CIDR를 붙이고 AZ별 파드 전용 서브넷을 생성한다.  
RFC 6598 대역으로 인터넷 라우팅 없이 VPC 내부에서만 사용된다.

### Terraform 변경 (`modules/vpc/main.tf`)

```hcl
resource "aws_vpc_ipv4_cidr_block_association" "pod" {
  count      = var.pod_cidr != null ? 1 : 0
  vpc_id     = aws_vpc.this.id
  cidr_block = var.pod_cidr  # "100.64.0.0/16"
}

resource "aws_subnet" "pod" {
  count             = length(var.pod_subnet_cidrs)
  vpc_id            = aws_vpc.this.id
  cidr_block        = var.pod_subnet_cidrs[count.index]
  availability_zone = var.azs[count.index]
  depends_on        = [aws_vpc_ipv4_cidr_block_association.pod]
  tags = {
    Name = "${local.prefix}-pod-${var.azs[count.index]}"
    # karpenter.sh/discovery 태그 의도적으로 제외
    # 추가 시 Karpenter가 pod 서브넷에 노드를 프로비저닝해 100.64.x.x primary IP 노드가 생성되고
    # VPC Interface Endpoint SG(10.10.0.0/16만 허용)에 의해 aws-node/kube-proxy ImagePullBackOff 발생
  }
}
```

dev 파드 서브넷:
- `ap-northeast-2a`: `100.64.0.0/17` (32,766 IPs)
- `ap-northeast-2c`: `100.64.128.0/17` (32,766 IPs)

### vpc-cni 설정 변경 (`modules/eks/main.tf`)

```hcl
resource "aws_eks_addon" "vpc_cni" {
  resolve_conflicts_on_update = "OVERWRITE"
  configuration_values = jsonencode({
    env = {
      ENABLE_PREFIX_DELEGATION           = "true"
      WARM_PREFIX_TARGET                 = "1"
      AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG = "true"   # 추가
      ENI_CONFIG_LABEL_DEF               = "topology.kubernetes.io/zone"  # 추가
    }
    enableNetworkPolicy = "true"
  })
}
```

`CUSTOM_NETWORK_CFG=true` 이후 파드 ENI는 ENIConfig에 명시된 서브넷에서 IP를 할당받는다.

### ENIConfig (Terraform `04-addons/main.tf`)

```hcl
resource "kubernetes_manifest" "eniconfig" {
  for_each = data.terraform_remote_state.network.outputs.pod_subnet_az_map

  manifest = {
    apiVersion = "crd.k8s.amazonaws.com/v1alpha1"
    kind       = "ENIConfig"
    metadata   = { name = each.key }  # "ap-northeast-2a", "ap-northeast-2c"
    spec = {
      subnet         = each.value
      securityGroups = [data.terraform_remote_state.eks.outputs.node_security_group_id]
    }
  }
}
```

### 적용 순서

```bash
# 1. secondary CIDR + 파드 서브넷 생성
cd terraform/environments/dev/01-network && terraform apply

# 2. vpc-cni CUSTOM_NETWORK_CFG 활성화
cd terraform/environments/dev/02-eks && terraform apply

# 3. ENIConfig 생성
cd terraform/environments/dev/04-addons && terraform apply

# 4. aws-node 재시작 (새 설정 반영)
kubectl rollout restart daemonset aws-node -n kube-system
```

### 적용 후 동작

```
새로 뜨는 파드  → 100.64.x.x (secondary CIDR)
기존 파드       → 재시작 전까지 10.10.x.x 유지
노드 자체 IP    → 10.10.x.x 그대로 (primary 서브넷 유지)
```

primary 서브넷은 노드 IP(1개/노드)만 소비하므로 Spot 노드 교체가 반복돼도 단편화가 재발하지 않는다.

## 5. Spot 인스턴스 전환 (`k8s/platform/karpenter/base/nodepools.yaml`)

### 배경

Secondary CIDR 적용으로 파드 IP 고갈 문제가 해소됐으므로 Spot 전환이 안전해졌다.  
SQS 기반 워커는 Spot 중단 시 visibility timeout 만료 후 자동 재처리가 보장된다.

### 변경 내용

**cpu-worker** — on-demand 고정 → spot 우선 + 인스턴스 패밀리 다양화

```yaml
# 변경 전
values: ["on-demand"]
values: ["m6i"]

# 변경 후
values: ["spot", "on-demand"]
values: ["m5", "m5a", "m6i", "m6a"]  # 동일 스펙(4 vCPU/16Gi), spot pool 확장
```

**gpu** — on-demand 고정 → spot 우선 + 2xlarge 추가

```yaml
# 변경 전
values: ["on-demand"]
values: ["xlarge"]

# 변경 후
values: ["spot", "on-demand"]
values: ["xlarge", "2xlarge"]  # g4dn.xlarge가 ap-northeast-2 spot 가용성 우수
```

`terminationGracePeriodSeconds: 300`(5분) + Karpenter interruption queue로 Spot 2분 notice 수신 시 drain 처리.

**batch-worker** — 인스턴스 크기 다운사이징

## 6. SQS visibility timeout 조정 (`modules/sqs`)

### 배경

EFS 모델 캐싱 미적용 결정. GPU 콜드 스타트(노드 프로비저닝 + 이미지 풀 + 모델 로딩)를 허용하는 대신, SQS timeout이 처리 도중 만료되지 않도록 설정값 점검이 필요했다.

### 타임아웃 적용 구간 이해

```
[노드 프로비저닝] → [이미지 풀] → [모델 로딩]
                                          ↓
                              SQS 메시지 pick up (ReceiveMessage)
                                          ↓
                              ← visibility timeout 카운트 시작 →
                                          ↓
                              [실제 추론/처리]
```

모델 로딩은 SQS 메시지 수신 **이전**에 완료되는 구조이므로,  
visibility timeout은 **실제 처리 시간만 커버**하면 된다.

### 문제: audio-preprocess 300s

`audio-preprocess-queue`는 기본값 `visibility_timeout_seconds=300(5분)`을 사용하고 있었다.  
cpu-worker에 `HF_TOKEN`이 있어 로컬 HuggingFace 모델을 사용함에도 별도 값이 설정되지 않아  
오디오 처리 시간이 5분을 초과하면 메시지가 큐에 재등장하고 `maxReceiveCount=3` 소진 후 DLQ로 빠질 위험이 있었다.

### 변경 내용

| 큐 | 변경 전 | 변경 후 | 비고 |
|----|---------|---------|------|
| audio-preprocess | 300s | **900s** | 전용 변수 신규 추가 |
| report-analysis | 900s | 900s | 유지 |
| gpu-inference | 1800s | 1800s | 유지 |
| rag-ingest | 300s | 300s | 텍스트 처리, 충분 |

`modules/sqs/variables.tf`에 `audio_preprocess_visibility_timeout_seconds` 변수를 추가하고  
`modules/sqs/main.tf`에서 해당 큐에 적용.  
dev, prod `03-services/main.tf` 양쪽에 900s 명시.

## 7. 핵심 교훈

1. **`kubectl logs`는 ContainerCreating 상태에서 아무것도 반환하지 않는다.** 원인 파악은 `kubectl describe pod`의 Events에서 시작해야 한다. CNI 계열 문제는 `aws-node`의 파일 로그(`/host/var/log/aws-routed-eni/ipamd.log`)를 `kubectl debug node`로 접근해야 실제 에러가 보인다.

2. **Prefix Delegation 모드에서 "가용 IP 수"와 "할당 가능 여부"는 다르다.** 112개 IP가 남아 있어도 /28 정렬 블록이 없으면 `InsufficientCidr`로 실패한다. VPC Console의 Available IPs 숫자만으로 문제 없다고 판단하면 안 된다.

3. **VPC Interface Endpoint는 각 AZ 서브넷에 ENI를 생성한다.** 노드 IP와 파드 IP가 같은 서브넷을 공유하는 구조에서는 Endpoint ENI가 서브넷 단편화를 가속한다. Secondary CIDR로 파드 IP를 분리하면 primary 서브넷의 단편화 요인을 노드 IP(1개/노드)와 Endpoint ENI로 한정할 수 있다.

4. **`ENABLE_PREFIX_DELEGATION=true` 환경에서 서브넷 크기를 `/24`로 설계하면 장기적으로 단편화 위험이 있다.** 최대 15개 /28 블록(240 IPs)이 한계이므로 노드 수가 늘어날수록 여유가 줄어든다. Secondary CIDR (`100.64.0.0/17` = 32,766 IPs per AZ)는 이 한계를 사실상 제거한다.

5. **SQS visibility timeout은 모델 로딩 시간을 포함하지 않는다.** 워커가 모델을 미리 로드한 뒤 SQS 폴링을 시작하는 구조라면, timeout은 순수 처리 시간만 커버하면 된다. EFS 같은 모델 캐싱 없이도 timeout을 충분히 길게 설정하는 것만으로 대응 가능하다.

6. **Spot 인스턴스 전환 시 인스턴스 패밀리를 여러 개 열어야 spot pool이 충분히 확보된다.** 단일 패밀리(예: m6i만)로 제한하면 해당 패밀리의 spot 가용성이 낮아질 때 on-demand로 폴백되어 비용 절감 효과가 감소한다.

## 8. Secondary CIDR 적용 후 파드 DNS 불통 — Security Group 불일치

### 8-1. 현상

Secondary CIDR 적용 완료 후 `utterai-api` 파드가 `Init:CrashLoopBackOff` 상태 유지:

```
sqlalchemy.exc.OperationalError: failed to resolve host
'utterai-dev-rds.c76womumyurf.ap-northeast-2.rds.amazonaws.com': [Errno -3]
Temporary failure in name resolution
```

새 노드(`ip-10-10-12-174`)에 새 파드를 올려도 동일한 증상이 재현됨.

### 8-2. 진단 과정

#### Step 1: ENIConfig/라우팅 확인 — 정상

```bash
kubectl get eniconfig
# ap-northeast-2a, ap-northeast-2c 모두 존재

kubectl get node ip-10-10-12-174... --show-labels | grep zone
# topology.kubernetes.io/zone=ap-northeast-2c  ✓
```

파드 IP `100.64.216.112` → secondary CIDR 서브넷 정상 배치.

#### Step 2: 노드 내 라우팅 규칙 확인 — 정상

```bash
# hostNetwork: true 파드로 확인
ip rule list
# 1536: from 100.64.216.112 lookup 2  ← 파드 → 라우팅 테이블 2

ip route list table 2
# default via 100.64.128.1 dev ens6   ← secondary ENI(ens6)으로 나가야 함
```

라우팅 설정 정상. iptables kube-proxy DNAT도 정상 확인.

#### Step 3: tcpdump — 쿼리는 나가지만 응답 없음

```bash
# 파드 노드(ip-10-10-12-174)에서 tcpdump
enia8b200f2208 In  IP 100.64.216.114.46377 > 172.20.0.10.53
ens6           Out IP 100.64.216.114.46377 > 10.10.11.208.53  ← DNS 쿼리 출력

# CoreDNS 노드(ip-10-10-11-248)에서 tcpdump
0 packets captured  ← 쿼리가 CoreDNS 노드에 도달하지 않음!
```

VPC 레벨에서 패킷이 드롭되고 있음을 확인.

#### Step 4: 보안 그룹 불일치 확인 — 원인 발견

```bash
# Karpenter 노드(ip-10-10-12-174) ENI
Primary ENI  (10.10.12.174):  sg-0dd5711ef7e2a2bbf + sg-0491be0ccad0f1c6a
Secondary ENI(100.64.250.250): sg-0dd5711ef7e2a2bbf  ← node SG만

# 관리 노드 그룹 노드(ip-10-10-11-248, CoreDNS 실행) ENI
Primary ENI  (10.10.11.248):  sg-0491be0ccad0f1c6a  ← cluster SG만
Secondary ENI(100.64.20.235): sg-0dd5711ef7e2a2bbf
```

- `sg-0dd5711ef7e2a2bbf` = `utterai-dev-eks-node-sg` (우리가 생성한 노드 SG)
- `sg-0491be0ccad0f1c6a` = `eks-cluster-sg-utterai-dev-eks-*` (EKS가 자동 생성한 cluster SG)

#### 트래픽 흐름과 차단 지점

```
파드(100.64.216.112) → secondary ENI [sg-0dd5711ef7e2a2bbf]
        ↓ DNS 쿼리(UDP 53)
CoreDNS 노드 primary ENI [sg-0491be0ccad0f1c6a]
        ↓
sg-0491be0ccad0f1c6a inbound 규칙:
  - All from self (sg-0491be0ccad0f1c6a) ← 자기 자신만 허용
  - ✗ sg-0dd5711ef7e2a2bbf는 허용 목록 없음
        ↓
DROP!
```

### 8-3. 해결

`modules/eks/main.tf`에 양방향 SG 규칙 추가:

```hcl
# 1. node SG에 cluster SG 전체 허용 추가 (aws_security_group.node ingress)
ingress {
  description     = "All traffic from EKS cluster SG (managed node group pods via Custom Networking)"
  from_port       = 0
  to_port         = 0
  protocol        = "-1"
  security_groups = [aws_eks_cluster.this.vpc_config[0].cluster_security_group_id]
}

# 2. cluster SG에 node SG 허용 추가 (별도 리소스 — EKS가 소유한 SG에 규칙만 추가)
resource "aws_vpc_security_group_ingress_rule" "cluster_from_node_sg" {
  security_group_id            = aws_eks_cluster.this.vpc_config[0].cluster_security_group_id
  referenced_security_group_id = aws_security_group.node.id
  ip_protocol                  = "-1"
  description                  = "All traffic from node SG (Custom Networking pod secondary ENIs)"
}
```

### 8-4. 근본 원인 정리

Custom Networking 이전 환경에서는 모든 파드 IP가 노드 primary ENI의 secondary IP로 할당되어 **cluster SG 하나**로 통신이 됐다.

Custom Networking 적용 후 파드는 **secondary ENI(node SG)**에서 IP를 받는다. 그런데 관리 노드 그룹 노드(CoreDNS, kube-proxy 실행)는 여전히 primary ENI에 **cluster SG만** 가지고 있다.

결과: `node SG → cluster SG` 방향 트래픽이 차단되어 pod→CoreDNS DNS 쿼리가 VPC에서 드롭됨.

**Custom Networking을 도입할 때는 node SG ↔ cluster SG 간 상호 허용 규칙이 반드시 필요하다.**

## 9. 핵심 교훈 추가

7. **Custom Networking에서는 Security Group 매핑이 달라진다.** 파드 secondary ENI는 ENIConfig에 지정된 SG를 쓰지만, 관리 노드 그룹은 EKS cluster SG를 primary ENI에 사용한다. 두 SG 사이에 상호 허용 규칙이 없으면 파드 간 통신(DNS 포함)이 VPC 레벨에서 모두 차단된다.

8. **tcpdump는 VPC 레벨 드롭을 노출한다.** 파드 노드에서 쿼리가 `ens6 Out`으로 나갔지만 CoreDNS 노드에서 `0 packets captured`면, 문제는 iptables/라우팅이 아니라 VPC Security Group이다. SG 진단은 `aws ec2 describe-security-group-rules`로 시작한다.

9. **ENIConfig의 `securityGroups`에는 cluster SG도 포함시켜야 한다.** 또는 `aws_vpc_security_group_ingress_rule`로 cluster SG에 node SG 허용 규칙을 추가한다. 어느 쪽이든 Secondary CIDR + Custom Networking 구성의 필수 설정이다.
