# LiteLLM 게이트웨이 검증 (2단계)

검증일: 2026-10-27. 원시 결과: [evidence/gateway-checks.json](../evidence/gateway-checks.json)

## 구성

```text
Slack 워커 ── slack-bot 키 ──┐
                             ├─→ LiteLLM Proxy ×2 (v1.104.2) ─→ Ollama (fast / quality / embed)
배치 요약 작업 ── batch 키 ──┘        │
                                PostgreSQL(키·사용량)  Redis(인스턴스 간 호출 제한 공유)
```

- 애플리케이션은 모델 이름 대신 별칭(`fast`, `quality`)을 부른다. 별칭 뒤의 실제 모델은 게이트웨이 설정에서 바꾼다.
- 서비스마다 키를 따로 발급한다. `slack-bot`은 `fast`만, `batch`는 `quality`만 쓸 수 있고, 키마다 분당 호출 수와 예산이 다르다.
- 게이트웨이의 자동 재시도와 fallback은 껐다. 재시도는 워커가 단독으로 관리한다. 두 곳에서 재시도하면 실패 한 번에 모델 호출이 몇 배로 늘 수 있다.
- 예산 검증에 쓴 단가는 테스트용이다. Bedrock 가격이 아니며 비용 추정으로 읽으면 안 된다.

## 결과

| 검증 | 결과 |
|---|---|
| 키별 허용 모델 | `slack-bot→fast` 200, `slack-bot→quality` 403, `batch→quality` 200, `batch→fast` 403 |
| 공유 호출 제한 | 분당 10회 키로 Proxy 2대에 번갈아 30회 요청 → 200 10회, 429 20회. 인스턴스별 카운터였다면 약 20회가 통과했을 것 |
| Redis 중단 중 호출 제한 | 같은 조건 20회 → 20회 모두 200. **Redis가 없으면 제한이 풀린다(fail-open)** |
| 예산 차단 | 응답 422(`budget_exceeded`). 예산 0.0005 대비 기록된 사용액 0.000755(1차), 0.002148(2차), 0.002059(3차). **차단 전 1.5~4.3배 초과**. evidence 파일에는 3차 실행만 남아 있다 |
| 게이트웨이 45초 중단 중 워커 (준비 상태 확인 없음) | 5개 모두 답변. 그러나 재기동 직후 `RemoteDisconnected` 5건으로 작업마다 시도 1회 소모(최종 시도 2회) |
| 같은 조건 (준비 상태 확인 있음) | 5개 모두 답변. 시도 소모 오류 0건, 작업마다 최종 시도 1회 |
| 작업별 사용량 | 워커가 기록한 토큰 수와 게이트웨이의 end-user 사용액이 테스트 단가 기준으로 일치(111토큰 → 0.000155). 게이트웨이 쪽은 묶어서 기록해 즉시 조회하면 404가 날 수 있다 |

## 실패 지점별 재시도 정책

| 실패 지점 | 판단 | 처리 |
|---|---|---|
| 연결 거부, 주소 조회 실패, 게이트웨이 429, 준비 상태 확인 실패 | 요청이 모델에 닿지 않았음이 확실하다 | 시도 횟수를 돌려주고 15·30·60·120·240·300초 간격으로 재시도. maxReceiveCount 8 기준 약 20분 장애까지 자동 복구, 그 이상은 DLQ |
| 401·403, 예산 초과(422) | 영구 거절 | 즉시 FAILED |
| timeout, 5xx, 응답 수신 중 연결 끊김 | 모델이 실행됐을 수 있다 | 시도 횟수를 소모(작업당 상한 2회) |
| 모델 결과 저장 뒤 Slack 실패 | 결과가 있다 | 저장한 결과를 재사용. 모델을 다시 부르지 않는다 |

### 검증하다 찾은 문제

처음 구현은 연결 거부만 "모델에 닿지 않음"으로 분류했다. 게이트웨이 중단 실험에서 모든 작업이 시도 1회를 잃었다. 원인을 추적하니, 컨테이너가 다시 켜질 때 Docker의 포트 전달기가 LiteLLM보다 먼저 포트를 열고 연결을 받았다가 끊었다(`RemoteDisconnected`).

클라이언트 입장에서 이 오류는 "요청을 보낸 뒤 끊김"이라 모델 실행 여부를 알 수 없다. 그래서 무조건 돌려주는 대신, 연결 단계 오류를 한 번 겪으면 다음 모델 호출 전에 `/health/readiness`를 먼저 확인하도록 했다. 확인 요청은 모델을 실행하지 않으므로 실패해도 시도를 돌려줄 수 있다. 정상 호출이 성공하면 다시 확인을 생략한다.

이 방식은 재기동 순간의 경쟁 구간을 줄일 뿐 없애지는 못한다. 확인과 호출 사이에 게이트웨이가 다시 멈추면 시도를 소모한다.

## 별칭별 모델 선택 측정

같은 질문 6개와 장애 근거 4종(잘못된 이미지 배포, 노드 부족, OOMKilled, 소비 정지)을 `fast`·`quality` 별칭에 보내 응답 시간, 토큰, 요약의 형식 준수와 근거 반영을 비교했다. 근거 반영은 핵심 단서(이미지 태그, CPU 부족, OOM, 소비 정지) 언급 여부로 판정한 간이 기준이다. 스크립트: `e2e/run_model_policy.py`

| 별칭 뒤 모델 | 질의응답 p50 | 질의응답 1,000회 비용 | 장애 요약 형식 / 근거 반영 |
|---|---|---|---|
| Bedrock Claude Haiku 4.5 (`fast`) | 2.4초 | $1.90 | 12/12 / 12/12 |
| Bedrock Claude Sonnet 4.5 (`quality`) | 6.6초 | $5.60 | 12/12 / 12/12 |
| 로컬 llama3.2:1b | 9.7초 | (참고용) | 3/12 / 0/12 |
| 로컬 qwen2.5:3b | 3.9초 | (참고용) | 12/12 / 12/12 |

- **결정:** AWS 구성에서는 질의응답과 장애 요약 모두 `fast`(Haiku)로 둔다. 요약에 필요한 건 "최소 Haiku급"이었고 Sonnet은 같은 결과에 3배 비용이었다. 키는 그대로 나눈다. 요약은 입력이 약 4배 크고(628 대 144토큰) 호출 빈도가 달라 호출 한도와 예산을 따로 둬야 한다.
- **로컬:** 로컬 `fast`(1B)는 요약을 하지 못해 `ops-advisor` 키는 `quality`를 쓴다.
- **로컬 소형 모델의 함정:** 토큰당 속도는 1B가 3B의 2배였지만 답을 4배 길게 써서 총 시간이 역전됐다. 또 1B는 프롬프트의 형식 예시를 되풀이했는데, 이것이 JSON으로 파싱돼 처음에는 형식 준수로 잘못 셌다.
- **런북이 근거를 이긴다:** 노드 부족 건에 크래시 런북을 잘못 붙였더니 큰 모델도 런북의 원인(연결 고갈, 메모리 누수)을 따라 적었다. 알림별 `runbook_url` 연결이 정확해야 하는 이유다.
- 비용은 토큰 수에 공개 단가(Haiku $1/$5, Sonnet $3/$15, 100만 토큰당)를 곱한 추정이다. Bedrock 측정은 서울 리전 global 추론 프로필로 2026-10-29에 한 번 실행했고 전체 약 $0.22였다. 원시 결과: [model-policy-bedrock.json](../evidence/model-policy-bedrock.json), [model-policy.json](../evidence/model-policy.json)

## 해석할 때 주의할 점

- **Redis 장애 시 fail-open:** 측정된 동작이다. 호출 제한이 비용 상한 역할도 한다면, Redis 가용성(관리형 Redis의 Multi-AZ 등)과 키 예산·모델 공급자 쪽 한도를 함께 둬야 한다.
- **예산은 소프트 상한이다:** 사용액을 비동기로 기록하므로 요청 속도와 기록 간격만큼 초과한다. 키별 분당 호출 수 제한이 초과량의 상한을 정한다. 예산을 엄격한 비용 차단 장치로 쓰면 안 된다.
- **로컬 모델 기준이다:** 토큰 수와 지연은 Ollama 소형 모델 값이다. Bedrock의 tokenizer와 출력 길이가 달라 비용 추정에 그대로 쓸 수 없다.
- **장애 재현 방식:** 게이트웨이 장애는 `docker compose stop/start`로 만들었다. AWS에서 로드밸런서 뒤에 둔다면 재기동 중 응답은 502·503 형태가 되며, 같은 분류 기준을 다시 확인해야 한다.

## 재현

```bash
docker compose -f gateway/compose.yaml --profile scale up -d
.venv/bin/python gateway/setup_keys.py      # 키는 gateway/.keys.local.json (gitignore)

```
