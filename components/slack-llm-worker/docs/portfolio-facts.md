# 포트폴리오에 쓸 수 있는 사실

수치는 모두 로컬 환경(LocalStack, kind, Argo CD, Gitea, LiteLLM 컨테이너, 모의 Slack) 기준입니다. 장애 시나리오는 실제 UtterAI 알림 기록(6/26~7/6)과 커밋 이력에서 가져왔습니다.

## 초안: 문제·원인 → 해결과정 → 결과

**Slack 장애 대응 ChatOps: 근거 수집과 GitOps 되돌리기**
Lambda · SQS · DynamoDB · Argo CD · Kubernetes RBAC · LiteLLM · Terraform · LocalStack · kind

**문제·원인**

- 음성 분석·리포트 생성이 단계별 큐와 워커로 나뉘어 있어, 장애 지점과 원인을 찾으려면 단계마다 큐 상태·Pod 이벤트·로그·최근 배포 이력을 따로 확인해야 해 대응이 오래 걸림
- Pod가 정상화되어도 큐 소비와 작업 완료가 재개됐는지는 따로 확인해야 하고, 그 결과를 팀에 다시 알려야 함
- 채팅 봇으로 옮기려 해도 Slack은 3초 안에 응답받지 못하면 요청을 다시 보내는데 LLM 답변은 그보다 오래 걸려, 모델 호출과 메시지가 중복됨
- 수시로 들어오는 질의응답·알림 요약과 요약 배치는 호출 빈도·입력량·허용 비용이 달라, 하나의 모델 사용 정책으로 묶기 어려움

**해결과정**

1. **단계별 장애 근거를 Slack 알림 하나로 수집**
   Pod 상태·종료 코드·Warning 이벤트, 배포 저장소의 최근 이미지 태그 변경, Argo CD 상태, 단계별 큐 대기·DLQ를 모아 알림과 함께 게시. LLM은 수집한 근거의 요약에만 사용.
2. **되돌리기 PR부터 처리 재개 확인까지 연결**
   크래시 직전 태그 변경이 있으면 되돌리기 PR을 제안하고, 봇은 PR만 열며 다른 사람이 승인·merge하면 Argo CD가 반영. 버튼을 진단한 커밋에 묶고 클릭 직전과 PR 대기 중의 배포 브랜치 변경을 감지해 반영을 차단. 반영 뒤 Argo CD 상태·새 Pod·재시작 횟수(파이프라인 단계는 큐 소비)를 확인해 같은 스레드에 공유.
3. **Slack 요청 접수와 처리를 비동기로 분리**
   Lambda에서 서명·타임스탬프를 검증하고 SQS 적재 후 3초 내 응답, 워커가 분석과 답변을 수행. 요청별 처리 상태와 생성 결과를 저장해 재전달 시 완료된 추론을 재사용하고, 전송 성공 여부가 불확실한 답글은 자동 재발송 대신 확인 대상으로 분리.
4. **LiteLLM Proxy로 용도별 모델 정책과 사용량 관리**
   질의응답·알림 요약·배치 요약에 키를 따로 발급해 허용 모델·호출 한도·예산을 설정. PostgreSQL에 사용량을 기록하고 Redis로 복제본 간 한도를 공유하며, 모델에 닿지 않은 실패는 재시도 횟수를 소모하지 않도록 분류.

**결과** (LocalStack·kind 기준)

- 6/30 실제 장애를 재현한 시나리오에서 알림 메시지 하나에 원인 단서(직전 이미지 변경 커밋, exit 1, CrashLoopBackOff)가 함께 표시되고, 되돌리기 PR 승인·merge 후 같은 스레드에 복구 확인
- 버튼 3회 동시 클릭에 PR 1개, 봇의 직접 merge는 거부(HTTP 405), PR 대기 중 새 배포가 생기면 merge 차단과 보류 알림
- 같은 이벤트 3회 전달에 모델 호출·답글 1회, 게이트웨이 45초 중단 중 재시도 소모 오류 5건 → 0건
- 원인이 배포가 아닌 노드 부족 Pending에는 근거만 제시하고 되돌리기는 제안하지 않음

## 면접에서 꺼낼 만한 이야기

- **설계에서 무엇을 바꿨나:** 재시도를 버리지 않음, DLQ 기준을 수신 8회로, RAG는 자료가 쌓일 때까지 보류하고 근거 수집으로 대신, 직접 재시작 대신 되돌리기 PR. 모두 실패를 재현하거나 실제 장애 기록을 보고 바꿨다. [design-mapping.md](design-mapping.md)
- **왜 재시작이 아니라 되돌리기 PR인가:** 실제 장애 6~7건 중 재시작으로 해결된 것이 없었고, 해결책은 모두 Git 변경이었다. ArgoCD 환경에서 클러스터를 직접 바꾸면 Git과 어긋난다. 그래서 봇은 클러스터를 읽기만 하고 PR만 연다.
- **검증하다 찾은 버그:** 늦게 처리된 클릭이 다른 장애에 PR을 열었다. 버튼이 진단한 커밋에 묶여 있지 않았기 때문이다. 같은 빌드의 다른 태그 이름 때문에 복구된 배포를 "복구 안 됨"으로 판정한 문제도 있었다.
- **LLM을 어디까지 믿었나:** 조치 제안을 측정해 보니 배포 직후 크래시에 3건 모두 재시작을 제안했고, 요약에도 근거에 없는 원인을 섞었다. 그래서 되돌리기 제안은 규칙으로, LLM은 요약으로만 썼다.
- **로컬 에뮬레이션의 한계:** LocalStack은 Function URL 공개 호출 권한이 없어도 요청을 받아 줘서, Terraform 이전 과정에서 빠진 권한을 놓칠 뻔했다.
- **왜 Slack인가:** 현업 표준에 맞췄다. Discord도 3초 응답 규칙이 같고, 메신저에 묶인 부분은 수신과 답글 전송뿐이다.

## 주장하면 안 되는 것

- "운영에 도입해 대응 시간 N분 단축": 실제 팀이 쓰지 않았다. 대응 시간 비교 측정도 없다.
- "EKS·GitHub·Slack에서 검증": kind·Gitea·모의 Slack 기준이다.
- "알림부터 복구까지 53초" 같은 시간: Argo CD 폴링을 15초로 줄였고 사람의 리뷰 시간이 없는 랩 수치다.
- "LLM이 원인을 진단": LLM은 수집한 근거를 요약할 뿐이고, 근거에 없는 원인을 섞기도 했다.
- "RAG·벡터 검색 구현": 구현하지 않았다. "운영 기록이 쌓이면 유사 장애 검색으로 확장할 수 있게 설계했다"까지만 말한다. 리포트 생성 서비스의 5-Agent RAG와 구분한다.
- "exactly-once": 전송 결과가 불확실하면 사람이 확인한다.
- "하루치 기록 요약 배치": 배치 요약은 넘겨받은 문장을 요약하는 예제 수준이다.
