# 포트폴리오에 쓸 수 있는 사실

이 워커에 한정한 문구와 근거입니다. 수치는 모두 로컬 환경(LocalStack, LiteLLM 컨테이너, Ollama) 기준이며 근거 파일을 함께 적었습니다.

## 초안: 문제·원인 → 해결과정 → 결과

**Slack 비동기 LLM 워커와 공용 LLM 게이트웨이**
Lambda · SQS · DynamoDB · ECS Fargate · LiteLLM · Redis · PostgreSQL · Terraform · LocalStack

**문제·원인**

- Slack은 3초 안에 응답받지 못하면 같은 이벤트를 다시 보내는데, LLM 답변은 그보다 오래 걸려 동기로 처리하면 같은 질문에 모델이 여러 번 실행되고 답글이 중복됨
- 서비스마다 모델을 직접 호출하면 키·호출 한도·비용이 흩어지고, 재시도가 실패 지점을 구분하지 않아 모델에 닿지도 않은 게이트웨이 장애만으로 시도 횟수와 모델 비용이 소모됨

**해결과정**

1. 수신(Lambda)과 실행(워커)을 SQS로 분리하고, 큐 적재를 확인한 뒤에만 Slack에 응답
2. DynamoDB 조건부 쓰기와 lease로 중복 전달된 작업을 한 번만 실행하고, 모델 결과를 먼저 저장해 Slack 재전송 때 모델을 다시 부르지 않음
3. Slack이 답글을 받았는지 알 수 없는 실패는 AMBIGUOUS로 격리해 자동 재전송을 멈춤
4. LiteLLM 게이트웨이 2대를 두고 서비스별 키에 허용 모델·분당 호출 수·예산을 부여, Redis로 인스턴스 간 호출 제한을 공유
5. 실패를 "모델에 닿지 않음 / 영구 거절 / 실행 여부 불명"으로 나눠 첫 번째만 시도 횟수를 돌려주고, 연결 오류 뒤에는 게이트웨이 준비 상태부터 확인
6. 인프라를 Terraform 모듈로 정의해 LocalStack에 적용하고 장애를 주입해 검증, 같은 모듈로 AWS 환경과 비용 가정을 정리

**결과**

- 고유 이벤트 100건, 3중 전달 20건에서 모델 호출과 답글이 각각 100회, 20회로 이벤트당 1회
- 게이트웨이 45초 중단 중에도 모든 작업이 답변, 시도 소모 오류 5건 → 0건
- 분당 10회 제한 키로 게이트웨이 2대에 30회 요청 시 10회만 통과
- AWS 월 비용 추정(약 $172)에서 인프라 비용의 87%가 게이트웨이 계층임을 계산해, 서비스가 하나면 게이트웨이 없이 직접 호출하는 편이 낫다는 도입 기준을 정리

## 면접에서 꺼낼 만한 이야기

- **검증하다 찾은 문제:** 게이트웨이 재기동 때 Docker 포트 전달기가 먼저 연결을 받았다 끊어서(`RemoteDisconnected`) 모든 작업이 시도 1회를 잃었다. 이 오류는 모델 실행 여부를 알 수 없어 무조건 돌려줄 수 없다. 그래서 연결 오류 뒤에는 모델을 실행하지 않는 준비 상태 확인을 먼저 하도록 바꿨다.
- **가정이 틀렸던 것:** 예산 초과 응답을 400으로 예상했는데 실제는 422였다. 그대로 두면 예산 초과를 재시도했을 것이다.
- **로컬 에뮬레이션의 한계:** Terraform으로 옮기면서 Function URL 공개 호출 정책 두 개가 빠졌는데, LocalStack은 이를 강제하지 않아 모든 검증이 통과했다. 원래 템플릿과 비교하다 발견해 복구하고 정적 테스트를 추가했다.
- **측정된 한계를 남긴 것:** Redis가 멈추면 호출 제한이 풀리고(fail-open), LiteLLM 예산은 소프트 상한이다. 그래서 비용 상한을 게이트웨이 하나에 맡기지 않고 Bedrock 할당량, AWS Budgets, 동시성 제한과 함께 둔다.
- **클라우드에서 검증하지 않은 이유:** 핵심 동작(큐, 조건부 쓰기, 재시도 분류)은 AWS 호환 API로 재현할 수 있어 로컬에서 반복 검증했다. 로컬로 증명할 수 없는 것(cold start, IAM, 실제 Slack 재시도, Bedrock 품질)은 따로 목록으로 두고, 1시간·1달러 미만 AWS 확인 시험 계획을 세웠다.

## ChatOps 확장에서 나온 이야기

- **LLM에게 실행 권한을 주지 않은 근거:** 배포 직후 크래시 루프처럼 재시작이 오히려 해로운 경우에 모델이 3건 모두 재시작을 제안했다. 그래서 LLM은 버튼을 띄울 수만 있고, 실행은 다른 운영자의 승인으로만 이뤄진다.
- **"결과를 모르면 멈춘다"와 "결과를 모르면 다시 한다"의 차이:** 답글 게시는 두 번 하면 중복이라 멈추고(AMBIGUOUS), 재시작은 승인 시각을 고정해 두 번 보내도 결과가 같게 만들어 다시 실행한다. 대상의 성질에 따라 재시도 정책을 다르게 설계했다.
- **방어를 두 겹으로:** 앱의 허용 목록에 실수가 있어도 Kubernetes Role이 `api` 하나만 patch를 허용해 막는다. LocalStack의 IAM과 달리 kind의 RBAC은 실제로 강제되므로 이 동작을 직접 확인했다.
- **ChatOps라고 부를 수 있는 이유와 한계:** 채팅에서 조회와 실행이 일어나고 팀 전체가 기록을 본다. 롤백, 스케일 조정, 실행 후 롤아웃 추적은 없다.

## 주장하면 안 되는 것

- "AWS에서 100건 동시 처리", "운영 ACK p95 1초", "cold start 포함 3초 보장": AWS에 배포하지 않았다.
- "exactly-once 답글", "중복·유실 완전 제거": 전송 결과가 불명확하면 사람이 확인한다.
- "비용 X% 절감", "월 $172로 운영": 측정값이 아니라 가정 기반 추정이다.
- "LiteLLM 예산으로 비용 차단": 측정 결과 소프트 상한이다.
- "IAM 최소 권한 검증 완료": LocalStack은 IAM을 강제하지 않는다.
- "벡터 RAG", "Bedrock 품질 검증": 구현·검증하지 않았다.
- "EKS에서 ChatOps 운영", "실제 Slack 버튼 검증": kind와 모의 Slack 기준이다.
- "LLM 제안 정확도 69%": 13건짜리 표본이라 비율로 일반화하지 않는다.
