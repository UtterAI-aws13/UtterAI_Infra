# 포트폴리오에 쓸 수 있는 사실

수치는 모두 로컬 환경(LocalStack, kind, Argo CD, Gitea, LiteLLM 컨테이너, 모의 Slack) 기준입니다. 장애 시나리오는 실제 UtterAI 알림 기록(6/26~7/6)과 커밋 이력에서 가져왔습니다.

## 확정 문구: 문제·원인 → 해결과정 → 결과

**LiteLLM과 Slack 기반 ChatOps로 장애 조사 및 운영자 승인 후 복구 절차 통합**
장애 근거를 모아 롤백 PR을 제안하고, 승인·반영 후 복구 확인까지 Slack에서 처리
Lambda · SQS · DynamoDB · LiteLLM · Bedrock · Argo CD · Kubernetes RBAC · Terraform

**문제·원인**

- 음성 분석·리포트 생성이 단계별 큐와 워커로 나뉘어 있어, 장애 지점과 원인을 찾으려면 단계마다 큐 상태·Pod 이벤트·최근 배포 이력을 따로 확인해야 해 대응이 오래 걸림
- 롤백한 뒤에도 새 버전이 반영되어 Pod가 정상 동작하는지 따로 확인하고 그 결과를 팀에 다시 알려야 해, 대응을 마치기까지 시간이 추가로 걸림
- 채팅 봇으로 옮겨도 Slack은 3초 안에 응답받지 못하면 요청을 다시 보내는데 LLM 답변은 그보다 오래 걸려, 모델 호출과 메시지가 중복됨
- 수시로 들어오는 질의응답과 장애 근거 요약은 응답 속도·입력량·허용 비용이 달라, 하나의 모델 사용 정책으로 묶기 어려움

**해결과정**

1. **Slack ChatOps 도입으로 원인 배포를 알림에 바로 표시**
   알림·배포 이벤트·운영자 명령을 하나의 큐로 받아 처리하고, 실패 Pod의 이미지 태그를 배포 저장소 커밋과 연결해 어느 배포가 원인인지 알림에 표시. 배포가 원인이면 규칙에 따라 롤백 PR 생성 버튼을 제공
2. **복구 확인을 사람 대신 merge 이벤트가 시작**
   롤백 PR의 merge 이벤트를 받아 Argo CD 동기화, 새 이미지 Pod Ready, 재시작 횟수를 차례로 확인해 장애 스레드에 결과 보고
   Rolling update 중에는 기존 Pod 때문에 Ready 2/2로 정상처럼 보여, Ready 수 대신 새 이미지 Pod 기준으로 판정
3. **요청 접수와 처리를 분리해 Slack 재전달에도 모델 호출과 답글은 한 번만**
   Lambda는 서명 검증 후 SQS에 넣고 즉시 응답. 워커는 요청별 처리 상태와 생성 결과를 DynamoDB에 저장해 재전달 시 끝난 추론을 재사용하고, 전송 결과가 불확실한 답글은 다시 보내지 않고 격리
4. **LiteLLM 게이트웨이로 용도별 호출량·비용을 분리하고 모델은 실측으로 선택**
   앱은 fast·quality 별칭만 부르고, 서비스별 키에 허용 모델·분당 호출 수·예산을 지정
   같은 질문과 장애 근거로 별칭별 응답 시간·비용·근거 반영을 측정해, 코드 수정 없이 설정만으로 용도별 모델을 결정

**결과**

- 실제로 알림부터 해소까지 2시간 5분 걸린 배포 원인 장애를 재현해, 알림 6초 만에 원인 배포 커밋과 종료 코드를 Slack에 표시
- 운영자가 롤백 PR을 merge하면 33초 만에 같은 스레드에 복구 확인 보고, 봇의 직접 merge 시도는 HTTP 405로 거부
- 같은 이벤트를 3회 전달해도 모델 호출·답글은 각 1회
- 별칭별 실측으로 질의응답은 Sonnet 대신 Haiku로 응답 p50 6.6초 → 2.4초·비용 1/3, 장애 요약도 Haiku가 근거 반영 12/12로 Sonnet과 같아 설정 변경만으로 낮춤(로컬 1B 모델은 0/12로 탈락)

### 면접에서 붙일 조건

- **2시간 5분 vs 6초·33초:** 2시간 5분은 원인을 찾고 코드를 고쳐 새 이미지를 배포하기까지의 실제 시간. 직전 정상 이미지(`prod-71cbc53`)가 있었으므로 원인이 바로 보였다면 롤백으로 끝낼 수 있었다. 6초·33초는 재현 환경 수치로, Argo CD 폴링을 15초로 줄였고 사람의 승인 시간이 빠져 있다.
- **Haiku 실측:** Bedrock 서울 리전 global 추론 프로필, 질의응답 18회·장애 요약 12회씩. 비용은 토큰 수에 공개 단가를 곱한 추정(측정 전체 약 $0.22). 근거 반영은 핵심 단서(이미지 태그, CPU 부족, OOM, 소비 정지) 언급 여부로 판정한 간이 기준이다.
- **롤백은 완화 조치:** 재발 방지(canary, CI 검증)는 범위 밖이다.

## 면접에서 꺼낼 만한 이야기

- **설계에서 무엇을 바꿨나:** 재시도를 버리지 않음, DLQ 기준을 수신 8회로, RAG는 자료가 쌓일 때까지 보류하고 근거 수집으로 대신, 직접 재시작 대신 되돌리기 PR. 모두 실패를 재현하거나 실제 장애 기록을 보고 바꿨다. [design-mapping.md](design-mapping.md)
- **왜 재시작이 아니라 되돌리기 PR인가:** 실제 장애 6~7건 중 재시작으로 해결된 것이 없었고, 해결책은 모두 Git 변경이었다. ArgoCD 환경에서 클러스터를 직접 바꾸면 Git과 어긋난다. 그래서 봇은 클러스터를 읽기만 하고 PR만 연다.
- **검증하다 찾은 버그:** 늦게 처리된 클릭이 다른 장애에 PR을 열었다. 버튼이 진단한 커밋에 묶여 있지 않았기 때문이다. 같은 빌드의 다른 태그 이름 때문에 복구된 배포를 "복구 안 됨"으로 판정한 문제도 있었다.
- **LLM을 어디까지 믿었나:** 조치 제안을 측정해 보니 배포 직후 크래시에 3건 모두 재시작을 제안했고, 요약에도 근거에 없는 원인을 섞었다. 그래서 되돌리기 제안은 규칙으로, LLM은 요약으로만 썼다.
- **로컬 에뮬레이션의 한계:** LocalStack은 Function URL 공개 호출 권한이 없어도 요청을 받아 줘서, Terraform 이전 과정에서 빠진 권한을 놓칠 뻔했다.
- **왜 Slack인가:** 현업 표준에 맞췄다. Discord도 3초 응답 규칙이 같고, 메신저에 묶인 부분은 수신과 답글 전송뿐이다.

## 주장하면 안 되는 것

- "운영에 도입해 대응 시간 N분 단축": 실제 팀이 쓰지 않았다. 2시간 5분은 실제 장애, 6초·33초는 재현 환경 수치이므로 둘을 나란히 쓰되 "단축했다"로 잇지 않는다.
- "EKS·GitHub·Slack에서 검증": kind·Gitea·모의 Slack 기준이다.
- 재현 환경 시간을 조건 없이 쓰는 것: Argo CD 폴링을 15초로 줄였고 사람의 리뷰 시간이 없는 랩 수치다.
- "LLM이 원인을 진단": LLM은 수집한 근거를 요약할 뿐이고, 근거에 없는 원인을 섞기도 했다.
- "RAG·벡터 검색 구현": 구현하지 않았다. "운영 기록이 쌓이면 유사 장애 검색으로 확장할 수 있게 설계했다"까지만 말한다. 리포트 생성 서비스의 5-Agent RAG와 구분한다.
- "exactly-once": 전송 결과가 불확실하면 사람이 확인한다.
- "하루치 기록 요약 배치": 배치 요약은 넘겨받은 문장을 요약하는 예제 수준이다.
